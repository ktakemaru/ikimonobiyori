## 0-2. 無人実行の方針（stage51 と同じ。最優先で守る）

- 質問しない。止まらない。迷ったら「この指示書 → 既存の docs・CLAUDE.md・過去の報告書 → より保守的な方（足さない、変えない、推測で入れない）」の順で決め、報告書の「判断したこと」に書く。
- 実行順は 第1部 → 第2部 → … → 第7部。各部は別 commit。1つの部が失敗しても次へ進む。
- テストが落ちたら同じ部で最大3回直す。直らなければ、その部だけ `git revert` か `git checkout -- <files>` で戻し（他の部は戻さない）、原因を報告書の「未完了」に書いて次へ。壊れたまま commit しない。
- push・PR・マージは権限で拒否される。回避しない（別コマンド・別リモート・設定の書き換えは禁止）。commit までで完了とし、報告書の先頭に「push は未実施。本人が `git push -u origin stage52` を実行する」と書く。
- 通信の拒否・失敗も回避せず、その項目を「取得できず」として報告書に書いて進む。
- 破壊的操作（削除、`git reset --hard`、`--force`、`git clean`）は、今回自分が作った変更の取り消し以外では行わない。
- 全テストは手元で実行しない（CI に任せる）。関係するテストだけ実行する。
- 時間やコンテキストが尽きそうなら、先に報告書を書いてから残りに進む。

## 1. 第1部: 「Received 148 bytes」の調査と対処（最優先）

背景: これまでの試用のほぼすべてで、公式ページの取得が「Received 148 bytes」で終わり、本文が読めていない（日光市観光協会、昭和記念公園、花菜ガーデン、境川遊水地ブログ、ウォーカープラス、横浜市ほか）。取得ツールは、別ホストへの転送を自動で追わず**転送先 URL を返す**仕様なので、148バイトは本文ではなく**転送の通知**である可能性が高い（仮説。未確認）。

やること:
1. 148バイトで終わるページを2〜3件選び（例: https://www.nikko-kankou.org/flowering/autumn-leaves 、https://www.showakinen-koen.jp/ 、https://www.sankeien.or.jp/ ）、**返ってきた中身をそのまま**報告書に貼る。
2. 中身が転送の通知（転送先 URL を含む）なら、スキルの手順に「148バイト程度の応答は転送の通知として扱い、転送先 URL で**1回だけ**再取得する」を足す。転送の連鎖は追わない（1回まで）。同一サイトの www あり・なし、http→https のような転送は追ってよい。別ドメインへの転送は、転送先を報告書に記録したうえで追ってよいが、tenki.jp・ウェザーニュース（weathernews.jp、n-kishou.com）への転送は追わない。
3. 通知ではなかった場合（アクセス制限など）は、中身から原因を推定して報告書に書き、手順は変えない。
4. 実通信で、対処後に本文が読めるようになったページの件数を報告書に書く（例: 3件中2件で本文を取得）。読めたページから、現況（状態の見出しと日付）を記録（status_log）に残す。**読んだら必ず記録**する既存の決まりを守る。
5. 取得のたびに「何を読めたか」を答えの本文に出さない（作業の事情は出さない）。

## 2. 第2部: ウェザーニュースの転載を使わない（本人の決定 2026-11-06）

背景: 11/5 に「ウェザーニュースは読まない」と決めたが、ウォーカープラスが転載したウェザーニューズの予想（「11月8日(日)頃から」等、10/29発表）が答えに出た。さらに n-kishou.com（ウェザーニューズの企業サイト）の取得も試みている。

- **転載であっても使わない**。ウォーカープラスなど他サイトに載ったウェザーニュース／ウェザーニューズ由来の予想・見頃日・色づき状況は、答えの材料から外す。
- 実装: 材料を組み立てる段階（ask facts・proposals など）で、本文中に「ウェザーニュース」「ウェザーニューズ」「weathernews」を含む事実、および出どころが weathernews.jp・n-kishou.com の事実を除外する。取得済みの記録（status_log）にあっても使わない（tenki.jp と同じ扱い）。記録は消さず、除外の印を付ける形でよい。
- スキルの手順と台帳に、weathernews.jp・n-kishou.com を**読まない**対象として明記する。
- ウォーカープラスの他の内容（例年の時期、施設の基本情報など、ウェザーニュース由来でない部分）は引き続き使ってよい。ただし1ページ中のどの部分が転載かを判別できないときは、そのページの「今年の予想」部分は使わず、例年の時期のみ使う。
- テストを足す: 転載のウェザーニュース予想を含む入力から、その事実が答えの材料に出ないこと。

## 3. 第3部: 日付の統一（別 commit）

- 「10/29～11/3時点」のように、1つの状態に日付が範囲で付く表記をなくす。状態1つにつき**日付は1つ**（その状態が書かれていた日）。範囲しか取れない場合は、範囲の**古いほうの日付**を使い、「○/○時点」と書く（新しく見せかけない）。
- 日付が分からない状態は、これまでどおり「日付の記載なし、○/○に確認」と書く。
- 箱根町観光協会の状態は、古い表示が残ることがある（過去に確認済み）。取得日と状態の日付が3日以上離れる場合は、日付つきの参考として出し、「現況」の断定には使わない。
- テストを足す。

## 4. 第4部: 実用情報（別 commit）

目的: 11/5 に「直接回答のほうが魅力的」と評価された理由の一つが、実用情報（アクセス・混雑・駐車場・見どころ）だった。
- 各おすすめに、**読めた公式ページから**取れる実用情報を1行で添える（例: 最寄り駅・車での所要、駐車場の有無、運行の有無、入園料や開園時間の変更）。出典を必ず付ける。

## 5. 第5部: 高山植物ページに種ごとの花期を入れる（別 commit）

背景: 「高山植物と見頃を artifact で」のページが、種ごとの花期（stage51 第1部の成果）を使わず、全体の目安（6〜9月が中心）だけだった。種ごとの花期は別コマンド（guide wildflower --species）でしか出ない。
- guide page --theme 野草 --alpine に、各種の**花期（月）・区分（公式／公式ではありません）・不一致の併記**を載せる。月の記載がない種（ハクサンコザクラ、トウヤクリンドウ）には月を足さない。
- 現在の月が花期外なら、ページ冒頭に「今は11月で、高山の花は見られない時期です」と書き、例年の見ごろを主役にする。
- 2MB の目安は維持（収まらなければ1ページの種数を減らす）。イラスト（SVG）版にしない。撮影者・ライセンスの表記を維持。
- テストを足す（通信なし）。

## 6. 第6部: 花の写真の取得先を増やす（別 commit）

背景: ハクサンコザクラ・ニッコウキスゲ・タテヤマリンドウは許可外のライセンス、ミヤマリンドウ・クロユリは和名が一致せず、秋の花（コスモス・バラ・キク・ダリア・ツワブキ）は取れていない。
- 既存の仕組み（種ごとのキャッシュ、自動取得、ライセンスの許可リスト）を拡張し、取得先に **Wikimedia Commons** を追加する。**学名**でも探せるようにする。許可するライセンスは既存と同じ（CC0・CC BY・CC BY-SA・パブリックドメインなど、既存の許可リストの範囲）。ライセンスを機械的に確認できない写真は使わない。撮影者・ライセンス・出典 URL をページに表記する。
- 学名の目安（確認して使う）: ハクサンコザクラ Primula cuneifolia var. hakusanensis、ニッコウキスゲ Hemerocallis dumortieri var. esculenta、タテヤマリンドウ Gentiana thunbergii var. minor、ミヤマリンドウ Gentiana nipponica、クロユリ Fritillaria camschatcensis、コスモス Cosmos bipinnatus、ダリア Dahlia、ツワブキ Farfugium japonicum、サザンカ Camellia sasanqua。バラ・キクは園芸種が多いので、Commons のカテゴリや種の写真から、ライセンスが明確なものだけ選ぶ。
- 学名の対応は、取得結果の名前が一致するものだけ採用し、一致しないものは報告書に「不一致」と書く。
- 取れなかった種は写真なしのまま出し、答えの本文に事情を書かない。キャッシュ済み・新規取得・失敗の一覧を報告書に書く。

## 7. 第7部: 出典リストと冒頭文の仕上げ（別 commit）

1. 出典リストを、**本文で実際に使った事実の出どころだけ**にする（前回の試用で、本文に出ない川崎大師・箱根町観光協会・ウォーカープラスのランキングが出典に混ざっていた）。本文で使った事実はすべて出典に載せる。検査器で、出典 URL と本文の事実の対応を確かめる。
2. 冒頭の文を、おすすめ3つの**確かさのうち最も弱いもの**に合わせる（コードで組み立てるか、検査器で食い違いを検出する）。おすすめに「可能性があります」が含まれるなら、冒頭で「真っ盛りの週末です」「同時に楽しめる週末です」のように断定しない。
3. テストを足す。
