## 3. フェーズA：写真つきページを標準にする（最優先）

### A-1. スキルの起動条件
`.claude/skills/ikimono-weekend/SKILL.md` と `CLAUDE.md`・`AGENTS.md` を書き換える。
- 「Artifact」「HTML」「ページ」「グラフィック」「図」「見せて」「写真」を含む依頼は、**対象によらず**、`guide page`（A-3 で花・野草に広げる）で作る。手でHTML・SVG を書かない。
- 順序: 答えを作る（これまでの手順）→ ページを作る → **Artifact ツールが使えれば、生成した HTML をそのまま Artifact として公開する**（HTML の中身を書き換えない。CSP・画像の埋め込みはコマンドが作ったまま）。使えなければ、絶対パスを 1 行で伝える。
- イラストの提案（「イラストつきにします」等）は、答えの末尾から外す。Artifact にもできる、は「写真つきのページにもできます」と書く。

### A-2. 写真の取得を確認なしにする（承認B）
- `CLAUDE.md` の絶対ルール6を「Python コードの実通信は、利用者がその場で認めたときだけ。**ただし写真の取得（`photos-*`）は、利用者の承認B（2026-11-03）により確認なしで行ってよい**」に書き換える（承認済み）。`ikimonobiyori/data/guide/policy.yaml` の `photos` の値の `source` に「ユーザー承認B 2026-11-03: 確認なしの自動取得（キャッシュにない種だけ）」と書き足す（上限・間隔・通信先は変えない）。
- `guide_photos.py` の `_gate` は、`--live`・`BIYORI_ALLOW_LIVE`・明示的な `--max-requests`・計測フック（`BIYORI_REQ_LOG`）を要求する。単体（`C:\ikimonobiyori`）にはハブの計測フックがない。**`livegate.py` は変えない**（ハブ側のテストが両方を比べる）。代わりに、新しいコマンド `guide photos-ensure`（A-3）が、通信先を policy の固定ホストに限り、既存の `photos_requests.jsonl` に件数を記録し、上限・間隔を守る形で、自分の中で許可を満たす。ハブ経由の実通信は従来どおり計測フックの下。
- 429 や自動アクセスの拒否が出たらそのホストは止め、その種は「写真なし」とし、理由を記録する（再試行は次の実行で）。ページの生成を止めない。

### A-3. `guide photos-ensure`（キャッシュにない種だけ補う）と、`guide page` への組み込み
- `python -X utf8 -m ikimonobiyori.guide photos-ensure --names <和名> ... [--theme 野鳥|花|野草] [--max-requests N]`: 対応表（和名 → 学名・taxon id）に無い種は表を作り（iNaturalist の taxa 検索）、写真のキャッシュに無い種だけ写真を取る。iNaturalist で取れなければ Wikimedia Commons。取れた分は種ごとに保存（`<IKIMONOBIYORI_DATA_DIR>/guide/photos/<taxon_id>.<ext>` と `.json`。既存の形）。**取れなかった種は「写真なし」として記録し、同じ実行・次の数回の実行で毎回探し直さない**（負のキャッシュ。有効期間は方針の値）。
- `guide page` に `--ensure-photos`（既定で有効）を足し、ページに出す種の和名を `photos-ensure` に渡してから組み立てる。1 回の実行の上限（既存の 80）に達したら、残りは「写真なし」で出し、**次の実行で続きを取る**（ページは作る）。
- 写真つきページの生成を、通信が使えない環境（オフライン）でも失敗させない。キャッシュだけで作る。

### A-4. 事前取得（毎回時間がかからないように）
- `guide photos-prefetch --theme 野鳥|花 [--all]`: 方針の一覧（A-5）にある種を、`photos-ensure` を 1 回 80 件以内に分けて、実行の間に方針の間隔をあけて繰り返す。バックグラウンドで実行してよい（`run_in_background`）。進み具合は記録（`photos_requests.jsonl`）で分かる。
- この段階の作業の中で、**野鳥・花の一覧（A-5）を実際に取得して、キャッシュを温めておく**（コミットしない）。

### A-5. 取得する種の一覧（方針に書く。値は `provisional: true`）
- 野鳥: 既存の対応表（25 種）に加え、関東の探鳥地（`ikimonobiyori/data/catalog/birds.yaml`・`wintering_birds.yaml`・`ikimonobiyori/data/observations/bird_areas.yaml` に出る種、東京港野鳥公園の記録に出る種）。調べて、100 種前後を目安にまとめる。
- 花: 名所カタログ（`data/catalog/flowers.yaml`）の `flower_kinds` と、段階32 の対象（秋バラ・菊・コスモス・ダリア）、桜（ソメイヨシノ・河津桜・冬桜・十月桜・寒桜）、梅、ひまわり、彼岸花、スズラン、アジサイ、ハナショウブ、フジ、ツツジ、芝桜、ネモフィラ、菜の花、スイセン、ラベンダー、ハス、サザンカ、ロウバイなどの主な花。
- 園芸品種（菊・バラ・河津桜など）で iNaturalist の種に当たらないものは、Wikimedia Commons の分類・カテゴリから取る。取れなければ属の代表写真、それでもなければ「写真なし」の枠（イラストにしない）。

### A-6. ページを軽くする
- **同じ種の写真は、ページ内で 1 回だけ埋め込む**。2 回目以降のカードは、同じ画像を参照する（CSP は `default-src 'none'; img-src data:; style-src 'unsafe-inline'` のまま、JavaScript を入れない。CSS の `background-image` に `data:` を 1 回だけ定義してクラスで参照する、など。方法は実装で決めてよい）。
- 取得するサイズは、方針の `photo_size`・Commons の `thumb_width` を見直して、カードの表示幅の 2 倍（スマホの高精細）で十分な値にする（値は `provisional: true`）。縮小・再圧縮はしない（Pillow を足さない）。必要なら提案として報告。
- 目安: 40 枚のカードのページで、**重複を除いて 2MB 以下**。超えたら、報告に原因を書く。

### A-7. ページの内容を良くする（F6〜F8）
- **結論と順位を先頭に置く**: 「今日のおすすめは○○です」の結論 → 順位つきの場所カード → 避ける場所 → 確かさの補足 → 次の質問 → 出典・写真のクレジット。ダークモード対応・スマホ幅で横スクロールなし。デザインは絵の版（`Zen Maru Gothic`・カード・チップ）を参考にしてよいが、**文はコマンドが作ったものを変えない**（既存の規則「文は変えない」）。
- **鳥の選び方**: 公園・探鳥地単位の記録（公式ブログ・観察の記録）がある鳥を先に出す。半径の集計は、「周辺でこの時期に多い鳥」と**区別して**出す（森に水鳥を出さないよう、探鳥地の環境タグ（`terrain`）と合わない鳥は外す。タグがなければ外さず、そう書く）。
- **記録の日付で分ける**: 「最近（7日以内）」「今季の記録（30日以内）」「過去の記録（日付つき）」。境界の日数は方針の値（`provisional: true`）。渡りの鳥の古い記録を「最近」に出さない。**10 年以上前のアルバム・記録は、根拠に使わない**（避ける場所に出す）。
- **まれな種**: その地域・その時期の過去の記録が少ない種（閾値は方針の値）は、おすすめの鳥に入れず「まれ」に分ける。亜種・別名は種に丸める（リュウキュウサンショウクイのような地域に合わない種を、そのまま出さない）。
- 写真のない種は「写真なし」の枠にしない: 同じ属の写真か、A-5 のとおり Commons を試し、それでも無ければ、カードを出さず「名前だけ」の行に回す。
- 鳥ごとに「見分けの目安」を短く添える（絵の版の良い点）。出どころは種のカード（A-5）か、出典つきの記述から。出典のない説明は書かない。

## 4. フェーズB：答えの質（全経路で共通に）

### B-1. 検査をすべての経路に通す
- 答えを出す経路を洗い出す（`ask` 経路／桜・梅などの `guide find --text` の経路／ひまわり等の検索だけで答える経路／聞き返しだけで終わる経路／ページ（A）の経路）。**どの経路でも、出す前に検査器（`ask verify` の規則）を通す**。通らなければ 1 回だけ直し、それでも通らなければ、通らない文だけ除いた final を出す。**検査を飛ばした答えを出さない**。検査に使う材料（facts）は、その経路が使った記録・検索結果から作る（神奈川の紅葉だけに作らない）。
- 答えに、検査・記録の事情を書かない。「検査器に通りませんでした」「final.txt の内容」「検査（ask verify）を実行していません」「記録していません」は出さない。**検査が落とした文は、利用者に見せない。**

### B-2. 内部の言葉・作業メモを答えに出さない（全経路）
- 禁止の言い方に足す（`data/ask/policy.yaml` の `forbidden_terms` など）: `作業メモ`、`guide find`、`record-candidate`、`policy.yaml`、`ask verify`、`ask record`、`ask`、`コマンド`、`スキル`、`テスト`、`コードは変更していない`、`検査`（作業の意味で）、`テーマの表`、`記録済み`、`提案として報告`。作業・開発の報告は、**答えとは別の場所**（作業フォルダのファイルや報告書）に書き、答えには出さない。段階37 の方針（コードを変更した作業のとき以外、テストの報告を書かない）を全経路に広げる。
- `find --text` の出力の誤字（「出どろ」）を直し、同種の誤字をテストで検出する（出力の項目名を定数にする）。

### B-3. 結論を先に、一覧は短く（桜・梅）
- `guide find --text` の出力の形を、**結論の 1〜2 文を先頭に**置き、おすすめ（最大 5）→ これから → 例年の時期の外 → 参考（**最大 5 件。残りは「ほか N 件」**）の形にする。「いつ頃から見られるか」の質問には、いまの時期から先の時期の順に、種類ごと（冬桜・十月桜／河津桜／ソメイヨシノなど）に 1 行ずつで答える。出力の変更に合わせてテストを書き換えてよい（一覧を報告書に）。

### B-4. 答えを出し切る・聞き返しで終えない（F12・F15）
- 手順書どおり、足りなければその場で検索して（1 質問あたり検索 8 回・取得 8 回まで）、見つけた事実を記録し、**答える**。「お答えできません」は、検索しても独立した出どころが 1 件も見つからないときだけ。**聞き返して終わる答え（候補 0 件で質問だけ）は、検査で落とす**（候補が 3 件未満のときは、見つかった範囲＋追加候補の出どころ）。
- 聞き返してよいのは、答えの**後ろに**「好みを 1 つ」だけ。
- 利用者が思い出した場所（「河口湖の近くのコスモス」等）は、検索で見つけた**近い候補を出どころつきで出し**、「ここでしたか」と末尾に添える。名前が分からなくても、地域・花の種類で名所カタログと検索から候補を出す（出どころが 1 件の仮は「仮」と書く）。

### B-5. テーマの穴を埋める（F13）
- 花の種類として、ひまわり・コスモス・彼岸花・スズラン・アジサイ・ハナショウブ・フジ・ツツジ・芝桜・ネモフィラ・菜の花・スイセン・ラベンダー・ハス（以上、既存でなければ）を、**既存の仕組み（花のプロファイルの種類 `flower_kinds`・名所カタログ・テーマの表）に足す**。足し方は既存の仕組みを調べて、最小の変更で。野草・高山植物は D で扱う。
- 新しい種類ごとに、**名所を検索して 5 件以上を候補として記録**する（`record-candidate` と同じ流れ。独立した出どころ 2 件以上で「定評」）。神奈川と、関東の近隣（250 km 内）を優先。
- **テーマを足せない質問でも、検索で見つけた名所を記録できる**ようにする（未登録の話題は「仮のテーマ」として候補を記録し、あとで種類に昇格できる）。知識が毎回貯まる形にする。

### B-6. 利用者が行った名所を活かす（F14）
- `origin: user`（利用者が実際に行った・確認した）の名所は、**出どころの数に関わらず、例年の時期に入っていれば「おすすめ」に出す**。答えには「あなたが行った場所」と書く（個人の訪問記録なので、日付は出さない）。時期に入らなければ「これから」「時期の外」に。出どころが公式でない・少ないことは「確かさ」に正直に書く。梅の曽我梅林・湯河原梅林で受け入れテストする。
- 実際に行った名所の記録の公式の出どころ（小田原市・湯河原町の梅まつり等）を検索で探して、見つかれば出どころに足す（自動）。

### B-7. 他のビヨリへの案内

### B-8. 取得の失敗（F16）

## 6. フェーズD：野草・高山植物（ネイチャーガイドの専門性）

目的: 利用者は野草・高山植物にとても興味があり、登山で見に行きたい。桜や梅に比べて専門性が高く、情報が一般的でない。イキモノビヨリの知識を厚くし、**プロフェッショナルなネイチャーガイド**として育てる。今年の開花状況は追わず、**例年いつ頃・どの標高・どの山域で**見られるか、**どんな花か**を、出どころつきで答える。

### D-1. 範囲
- 山域 = `ikimonobiyori/data/sites.yaml` の山・山域 76 地点（yamabiyori の `MOUNTAINS` の複製）。地点の座標・標高・山域名・都道府県を読み、**山域のまとまり**（例: 丹沢・箱根・奥多摩・高尾・富士山・八ヶ岳・南アルプス・北アルプス・上信越 など。`sites.yaml` の持つ区分に従う）で扱う。出発地（横浜）から日帰り〜1泊で行ける範囲を優先して深くし、アルプスなどの高山は、代表的な高山植物と見頃（例年）を出どころつきで。
- 野草は、里〜低山（秋なら リンドウ・ノコンギク・シラヤマギク・ツリガネニンジンなど）から、亜高山・高山（夏のお花畑）まで。**ただし、ここに書いた種名は例であり、事実は必ず出どころから取る**。記憶で書かない。

### D-2. 知識の出どころ（ネット上の情報を自分で探す）
- WebSearch・WebFetch で、公開ページを自由に読む（段階34 の方針。確認しない）。出どころの候補: 国立公園・自治体・観光協会の花ごよみ、ビジターセンターの資料、植物園・博物館（神奈川県立生命の星・地球博物館など）、環境省・林野庁の資料、登山口・山小屋・ロープウェイの運営者の発信、山と自然の専門メディア、図鑑系の解説（本文を写さず、事実だけ）、登山記録サイト（個人の発信。`secondary` の区分で、独立した出どころの数に数えるのは別途の方針の値）。
- 出どころの区分・日付・URL を付けて記録する。**独立した出どころが 2 件以上で「定評」**（花の野草は方針の値。provisional）。1 件は「仮」と書く。本文の長い引用・写し・写真は残さない。自動アクセスを拒否されたページは読まない。

### D-3. 種のカード（知識の核）
- 保存先は既存の流儀に従う（`ikimonobiyori/data/guide/` に、種の表 `wildflower_taxa.yaml` と、種ごとの事実 `wildflower_facts.yaml` など。スキーマは `ikimonobiyori/schemas/` に足し、jsonschema の検査に通す）。1 種のカードの項目: 和名・学名・iNaturalist の taxon id・科・**標高の範囲**・**例年の開花期（月・旬）**・生えている環境（草原・林縁・岩場・湿地・雪渓など）・見分けのポイント・似た種との違い・**注意（採取禁止・保護種・毒・踏み荒らし）**・出どころ（URL・読んだ日・区分）・確度（独立した出どころの数）。
- 最初の投入の目安（`provisional`）: 里〜低山の野草と、関東〜中部の山で人気の高山植物を、**100〜150 種**。多すぎて質が落ちるなら、**質を優先して少なくしてよい**（出どころの付いたものだけ）。
- 保護: 盗掘の恐れのある希少種（ラン科・高山の希少種など）は、**具体的な場所（地点）を出さず、山域まで**にする。採取しない・登山道から出ない・踏まないことを、答えの「注意」に必ず添える。

### D-4. 山域ごとの花暦（例年の時期）
- 山域 × 月（旬） × 標高帯 の表 `wildflower_calendar.yaml`。各行に、見られる種（D-3 への参照）と出どころ。**ネットの花ごよみ（登山口・ビジターセンター・観光協会）から作る**。標高が上がるほど時期が遅れる点（標高 100m ごとの遅れの目安）は、出どころのあるときだけ書く。
- 優先順: 丹沢・箱根・奥多摩・高尾 → 富士山周辺・八ヶ岳・南アルプス → 北アルプス・上信越・東北の近い山。時間が足りなければ、優先の高い山域から深く。浅い山域は「準備中」と答えに明記する。

### D-5. 観察記録による裏づけ（iNaturalist）
- 野鳥の `bird_areas.yaml` と同じ考え方で、山域（座標・半径）ごとの**植物の観察記録（研究グレード）の月別・標高帯別の件数**を集計し、花暦の裏づけにする。通信は A-2 の承認B と同じ範囲（api.inaturalist.org。間隔 1 秒以上・1 回 80 件以内。実行を複数回に分ける）。**記録は集計だけ保存**（観察者・正確な座標・写真の URL を保存・出力しない。絶対ルール7と同じ丸め）。
- 文献（出どころつきの花暦）と観察の集計が食い違うときは、答えに両方を出し、「観察の記録では○月に多い」と書く。希少種は集計を出さない。

### D-6. 答え方（質問の型）
- 質問例: 「野草にとても興味があります。登山で見に行きたい。見頃と場所を教えて」「11月でも見られる野草は?」「5月の丹沢で見られる野草は?」「夏に高山植物が見られる山は?」「リンドウが見られる山は?」。
- 答えの形: 結論（いまの時期＝質問の日の月に見られる野草と、おすすめの山域）→ 山域ごとに、見られる野草（標高・例年の時期・見分けのポイント）→ 「これから」（次の月に見頃になる野草）→ 避ける・注意（採取禁止・標高と時期のずれ・天候）→ 確かさ（「今年の開花は読めていません。例年の時期の目安です」と書く。出どころの数と区分）→ 出典 → 好みを 1 つ。**今の開花状況を言い切らない**。
- 日付つきの現況（ビジターセンター・山小屋の発信）が検索で見つかれば、日付つきで「今年の様子」に添える（任意）。無ければ書かない。
- 山の天気・登山の計画（コース・危険箇所・日没）は扱わず、「ヤマビヨリで確かめてください」の一言だけ（B-7）。
- 野草の質問も、対象を指定しない質問（「今日のおすすめ」）に含めるかは、既存の `topics` の方針に従い、**野草の語（野草・山野草・高山植物・お花畑・〇〇が見たい）を話題として登録**する（`sources topic`）。

### D-7. 知識を育てる流れ（自動）
- 質問に答えるたびに、検索で見つけた事実（種・開花期・標高・山域・出どころ）を**自動で記録**する（種の候補 → 出どころが 2 件になれば定評へ昇格）。利用者が「行った」「見た」と教えた場所・花は `origin: user` で記録する（B-6）。
- `catalog_audit` に、野草の点検（出どころのない種・標高と開花期の矛盾・保護種の場所の出力・山域ごとの被覆率）を足す。結果を報告書に書く（通信しない）。

### D-8. 写真
- 野草の種のカードに、A の仕組みで写真を付ける（iNaturalist の研究グレードの代表写真。ライセンスは方針の値）。写真のない種は「写真なし」。**希少種の写真は、場所が特定されないものだけ**（iNaturalist の位置の秘匿を尊重。写真の位置情報は使わない）。
