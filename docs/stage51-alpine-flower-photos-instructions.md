## 2. 第2部: 季節の花の写真（フェーズC、別 commit）

方針（本人の決定を反映。判断が分かれる箇所は下記のとおりに決めて進める）:
1. 野鳥の写真と**同じ仕組み**（種ごとのキャッシュ、確認なしの自動取得、取得できなかった種は自動取得で補い事前取得の一覧に足す）を花にも広げる。まず docs\stage39-report.md と、野鳥の写真の実装（段階39〜40）を読み、重複する仕組みを作らず拡張する。
2. 対象は**花の種**: 秋〜冬の花（コスモス・秋バラ・菊・ダリア・サザンカ・ツワブキ・ロウバイ・水仙・河津桜ほか、カタログの旬の花）と、第1部の高山植物（チングルマ・ハクサンコザクラ・ミヤマキンバイ・コマクサ・トウヤクリンドウ・ニッコウキスゲほか）。
3. 写真は**ライセンスが明確なものだけ**を使い（野鳥と同じ取得元・同じ条件）、撮影者・ライセンスの表記をページに出す。表記が取れない写真は使わない。
4. 写真つきページ（guide page）に花の写真を出す。ページ全体は2MBの目安（本人が変更可としている目安）に収め、収まらないときは1ページの種数を減らす（「今見られる＝月」「この山＝山域」「全部＝図鑑で季節ごと」の切り方は維持）。イラスト（SVG）版にはしない。
5. 紅葉の写真は**今回は樹種の写真（イロハモミジ・イチョウ・ケヤキ等）まで**とし、地点そのものの写真は扱わない（権利と取得の手間のため。報告書に「地点写真は未着手」と書く）。
6. 取得は種単位でキャッシュし、2回目以降は通信しない。キャッシュ済みの種を一覧で報告書に書く。
7. 取得に失敗した種は、そのページで写真なしのまま出し、答えの本文に作業の事情（失敗した旨）を出さない。

## 3. 第3部: 試用で見つかった答えの崩れの修正（別 commit。第1・第2部が終わってから）

2026-11-06 の試用（「今週末、紅葉や花、野鳥を楽しめるところを教えて」）で見つかった5点。段階26・段階17で直したはずの型の再発を含むので、**原因（なぜ再発したか）も調べて報告書に書く**。

1. 答えの末尾に作業報告（「11/6 に東京港野鳥公園の1ページを読み直し、新しい記録が1件増えました」「日光市観光協会・昭和記念公園ほかも読みに行きましたが、新しい情報は取れませんでした」）が出ている。使う人には「何月何日時点か」だけ示す決まりなので、答えの本文・末尾に作業の事情を出さない。検査器に、この型の文（「読みに行きました」「記録が○件増えました」「取れませんでした」等）を禁止語として足し、再発を防ぐテストを足す。
2. 冒頭の要約（近場で菊と野鳥、少し足を延ばして庭園、遠出で日光）と、「今回のおすすめ」の3つ（三溪園・東京港野鳥公園・中禅寺湖）が食い違う（庭園＝昭和記念公園がおすすめに入っていない）。冒頭の文は、おすすめの3つから**コードで組み立てる**か、検査器で食い違いを検出して落とす。
3. 「鶴見川多目的遊水地」の行が、公園で見られる鳥の話に読めるが、実際は神奈川県全体の季節傾向（iNaturalist）。県全体の傾向である旨を明記し、公式でないので「公式ではありません」を添える。
4. 出典リストと本文が対応していない（花菜ガーデンと iNaturalist の URL がない。「ローズフェスティバルは11/8まで」の根拠が出典にない）。本文で使った事実の出典を、出典リストに漏れなく出す。根拠のない事実は書かない。
5. 見込みの書き方が断定的（「週末は見ごろに入る時期です」）。日光のページは今回の取得が失敗していた。例年の時期と3日前の記録から言い切らず、「見ごろに入っている可能性があります」程度に弱める。公式の文を丸ごと転載せず、状態の見出し（「◎ 真っ盛り」など）は原文のまま、それ以外は短くまとめる。
