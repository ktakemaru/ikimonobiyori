## 0-2. 無人実行の方針（最優先で守る）

- 質問しない。止まらない。迷ったら「この指示書 → 既存の docs・CLAUDE.md・過去の報告書 → より保守的な方」の順で決め、報告書の「判断したこと」に書く。
- 実行順は 第1部 → 第2部 → … → 第7部。各部は別 commit。1つの部が失敗しても次へ進む。
- **テストは、変更した部ごとに、関係するテストに加えて、全テストを手元で1回実行してから commit する**（約5〜10分。段階54で、関係するテストだけで済ませて CI が全件落ちたため）。落ちたら原因を調べて直す（同じ部で最大3回）。直らなければ、その部だけ `git revert` か `git checkout -- <files>` で戻し、原因を報告書の「未完了」に書いて次へ。テストの期待値や条件を緩めたり、テストを削除したりしない。
- push・PR・マージは権限で拒否される。回避しない。commit までで完了とし、報告書の先頭に「push は未実施。本人が `git push -u origin stage56` を実行する」と書く。
- 通信の拒否・失敗も回避せず、その項目を「取得できず」として報告書に書いて進む。通信を伴う部は、取得の回数に上限を置き（第6部: 最大250回）、直列・同じホストへは1秒以上あける・失敗が10回連続したら中断。robots.txt で拒否されているページは取得しない。
- 破壊的操作（削除、`git reset --hard`、`--force`、`git clean`）は、今回自分が作った変更の取り消し以外では行わない。
- 各部が終わるたびに docs\stage56-progress.md に追記する。時間やコンテキストが尽きそうなら、先に進捗と報告書を書いてから残りに進む。
- **報告書の正確性**: 答えの候補をどう選んだか（コードか、手での選択か）を、**事実のとおりに**書く。コードがしたことと、人（エージェント）が判断したことを区別する。

## 2. 第1部（最優先）: `ask plan` — 答えの計画をコードで作る

新しいコマンド（例: `python -m ikimonobiyori ask plan --query "来週末の紅葉" --date 2026-11-14`）を作る。名前は既存のコマンド体系に合わせてよい。

### 2-1. 入力と出力

- 入力: 質問の種別（紅葉／花／野鳥／総合）、対象日（今日・今週末・来週末・指定日）、出発地（既定は横浜）。
- 出力: **計画（JSON）** — 狙い別の節、各節の採用と順位、全体の「今回のおすすめ」3件、不採用の一覧と**理由コード**。

### 2-2. 候補の評価（点数）

各候補に、次の要素から点数を付ける。重みは policy.yaml（または既存の設定）に置き、コードに埋め込まない。

1. **対象日の見込み**（最も重い）: 現況・日光市観光協会などの「見頃予測」・例年の窓から、コードで区分を出す（見頃中の見込み／見頃に向かう／終盤の見込み／過ぎている見込み／不明）。
2. **現況の新しさ**: 日付が新しいほど高い（古いものは減点。日付なしは低い）。
3. **距離**: 近いほど高い（狙いによって重みを変える。「近場」では重く、「絶景・遠出」では軽く）。
4. **まつり・行事の加点**: 対象日がまつり期間内、ライトアップ期間内なら加点（ただし**現況の代わりにはしない**）。
5. **実用情報の有無**: 開園時間・アクセスなど、読めた公式の実用情報があれば小さな加点。
6. **出どころの確度**: 公式＞紹介。ただし公式でないことを理由に落とさない（共通の決まり）。

### 2-3. 狙い別の節

- 節の種類（既存の規則に合わせる）: 近場で手軽に（目安50km以内）／歩いて楽しむ・山歩き／絶景・遠出（目安100km以上）／夜・ライトアップ／ドライブ。**該当する候補がある狙いだけ**節を作る。
- 各節で、点数の上位1〜3件を採用する。
- 全体の「今回のおすすめ」は3件。節ごとの1位から、見込みの高い順に選び、**狙いが分散する**ようにする（近場1・歩く1・遠出1 など）。

### 2-4. 不採用の理由コード（内部用。答えには出さない）

過ぎている見込み／距離が遠い（狙いに合わない）／現況なし／現況が古い／同じ狙いに上位がある／重複（同じ地域）／承認待ちの情報源のみ／範囲外。候補ごとに記録し、`ask plan --explain <名所>` で、順位と理由が見られるようにする。

### 2-5. スキルとの関係（重要）

- スキル ikimono-weekend の手順を、「**plan の採用だけを文章にする**」形に書き換える。plan にない名所を足す・差し替える場合は、plan にその**理由を記録**してから行う（`ask plan --override <名所> --reason <理由>`）。
- 検査器（ask verify）に、**答えの採用と plan の照合**を足す: plan の「今回のおすすめ」と答えの①②③が食い違う、または plan にない名所が理由の記録なしに出ていたら不合格。
- 1週間以上先の見込みの言い回しは、見込みの区分から、**言い切りにならない定型の候補**（「見頃に向かう可能性があります」「見頃が続いている可能性があります」「終盤の可能性があります」「見頃を過ぎている可能性が高いです」）を plan が出す。検査の now_peak_claim に触れないこと。
- 答えの文字数の上限（1500字）はそのまま。**上限を理由に節や候補を落とす処理は作らない**（超える場合は文章を短くする）。

### 2-6. 受け入れ条件

- 2026-11-07 の時点の記録で「来週末の紅葉」の plan を作ると、候補に**国営昭和記念公園、日光（中禅寺湖・日光の社寺）、丹沢・陣馬山・大山、長瀞、御岳山、町田薬師池、高尾山、箱根**が入り、それぞれの順位と不採用の理由（採用の場合は点数の内訳）が見られる。「見頃を過ぎている見込み」の候補（霧降滝、中禅寺湖など）は、見込みの区分どおりに扱われる。
- plan の「今回のおすすめ」が、近場・歩く・遠出に分散している。
- 合成データでテストを足す（通信なし）: 点数の並び、狙いの分散、不採用の理由コード、override の記録、答えと plan の食い違いの検出。
- 回帰テスト（22問）に、plan を通す形を足し、**期待値は勝手に緩めない**。

## 5. 第4部: 答えの文面の不具合の修正（別 commit）

段階55の答えで見つかった不具合。plan とは別に直す。

1. **見頃の終了日を過ぎた場合の書き方**: 例年の見頃が「10/1〜10/20」で今日が11/7のとき、「今週末は終盤の可能性があります」と書く不具合（ソレイユの丘）。終了日を過ぎていれば「見頃を過ぎている可能性が高いです」にする。
2. **1日だけの行事の書式**: 「あと22日で開始(11/29〜11/29)」「主催者が設定した期間: …」を、「11/29（日）」「あと22日」の自然な形にする。ラベルは、期間があるまつりにだけ使う。
3. **出典 URL**: iNaturalist はトップページではなく、実際に使った URL（観察記録のページ・検索条件）を出す。作れなければ、出典に出さず本文でも「iNaturalist の記録」と書く。
4. **文の重複**: 「例年の見頃は、…例年10月中旬〜…」のような「例年」の重複をなくす。
5. 各修正に、合成データのテストを足す。
