## 1. 目的

ビヨリコンシェルは段階 4 で、イキモノビヨリの資料(`ask brief` の JSON。`ikimonobiyori-guide-brief/1`)を読み、山・星と合わせて一日の流れの案を作ります。
前回の調べ(`docs/concierge-brief-fields.md`。main `72a11ad`)で、資料の候補に次の 3 つが無いと分かりました。これを足します。

| 足すもの | コンシェルでの使い道 |
|---|---|
| 候補の座標 | 山・星の地点からの直線距離(20km 以内)を計算して、「日中」の枠に近くの名所を入れる |
| 候補の変わらない ID と、山の地点との結びつき | 名所を名前でなく ID で見分ける。山の ID(`yamabiyori:mNNN`)と突き合わせる |
| 資料を作った版 | どの版・どの commit のイキモノビヨリが作った資料かを記録する |

**決まり: 項目の追加だけ。答えは 1 文字も変えない。** スキーマの名前は `/1` のまま。

ブランチは 1 本: `feature/brief-concierge-fields`(main から)。

## 2. 作業の決まり

- **通信しない。** Web 検索・ページの取得・iNaturalist・Open-Meteo への通信をしない。`ask brief` を実通信つきで実行しない(確かめは、前回と同じ「通信を禁じたテストの仕組み」の下で `guide_brief.build` を呼ぶ形で行う)。
- commit まで。push・PR・マージ・タグ・版上げは利用者(版は 0.2.0 のまま。CHANGELOG は未公開の節に書く)。
- **変えないもの**: 候補の選び方・順位・点数・距離の計算、事実・知識カードの中身、資料の Markdown(`<id>.md`)、今までの形の答え(`fallback`)、答えの照合(`ask verify`)の合否、情報源の台帳と承認の状態、名所カタログ・`data/sites.yaml` の中身。
- **座標・ID を新しく作らない。** 足す値は、名所カタログ・`data/sites.yaml` など、**リポジトリに今あるデータから写すだけ**。データに無い候補は `null`。住所や名前から座標を調べない・推測しない。
- 足した項目を、資料の Markdown と答えを書くときの決まり(`rules`)には出さない(AI が答えに緯度・経度や ID を書かないようにするため)。JSON にだけ入れる。
- **改行コードを変えない。** commit の前に `git diff --stat` を見て、直した量に比べて行数が不自然に多いファイルがあれば、改行コードを確かめて元に戻す。
- 既存のテストの期待値を、通すために書き換えない。例外は、資料の項目の名前を全部並べて見ているテストだけ(名前・変えた行・理由を報告書に並べる)。
- テストは、変更に関係するものだけを実行する(全テストは CI に任せる決まりのまま)。実行したテストの最後の行を報告書に書く。
- `git add -A` を使わない。「!」のコマンドは Git Bash で動くので、パスは `/` で書く。外部ライブラリを足さない。

**止まる条件**(第 0 部で確かめる。当たったら何も変えずに、理由を 3 行で書いて止まる)

- 追跡中のファイルに未 commit の変更がある(`git status --porcelain --untracked-files=no` が空でない)。
- main が `72a11ad` を含んでいない。
- `docs/concierge-brief-fields.md` が無い。

## 3. 第 0 部: 始める前の確かめ

1. `git status`・ブランチ・`git log -1` を控える。`docs/concierge-brief-fields.md` を読む。
2. **直す前の資料を取る**: 前回と同じ 5 つの質問(「今週末、高尾山で紅葉を見たい」「今週末の紅葉の情報は?」「丹沢で今咲いている花は?」「八ヶ岳の見どころを教えて」「高尾山の見どころを教えて」)に、次の 3 つを足した 8 つで、決まった `now` の資料(JSON と Markdown)を作り、`C:/temp/ikimono-brief-fields-20261127/before/` に保存する。
   - 「今週末、野鳥を見に行きたい」/「今週末のおすすめは?」/ 地域を指定した質問を 1 つ
3. **候補の出どころを調べる**: 候補の種類(`basis` が `current`・`typical`・`species`・`town` など)ごとに、候補がどのデータ(名所カタログ・`data/sites.yaml`・行事の台帳・町の一覧 など)から作られるか、そのデータに ID・座標・`site_ref` があるかを表にする。**この表を先に報告書に書いてから実装する。**
4. `git switch -c feature/brief-concierge-fields`。この指示書(`C:/temp/ikimonobiyori-brief-fields-instructions.md`)を `docs/brief-concierge-fields-instructions.md` に写して commit。

## 4. 第 1 部: 候補に ID・座標・山との結びつきを足す

`candidates[]` の 1 件に、次の項目を足す(名前は、今の提案の出力 `biyori-proposal/1` で使っている名前に合わせられるなら合わせる。合わせた・合わせなかった理由を報告書に書く)。

| 項目 | 中身 | 無いとき |
|---|---|---|
| `place_id` | その名所の変わらない ID(名所カタログなら `ikimonobiyori:<id>`、山なら `yamabiyori:mNNN`) | `null` |
| `lat`・`lon` | 緯度・経度(元のデータの値をそのまま。丸めない) | `null` |
| `coord_source` | 座標の出どころ(どのデータから写したかの短い語) | `null` |
| `site_ref` | 山の地点との結びつき(`yamabiyori:mNNN`)。元のデータに結びつきがある候補だけ | `null` |

- 候補をまとめた記録(`candidate_merges`)があるときは、まとめた先の候補にどの ID・座標を入れたかが分かるようにする(食い違えば `null` にして、食い違いを今ある `candidate_merge_conflicts` と同じ考え方で残す。新しい決まりを作らず、分からなければ `null`)。
- 出発地からの距離(`distance_km`)は今のまま。足した座標から計算し直さない(食い違いが見つかったら、直さずに報告書に書く)。
- **`null` の候補を数える**: 8 つの資料で、候補の種類ごとに、ID・座標が入った件数と `null` の件数を表にして報告書に書く。`null` が多い種類は、どのデータに何を足せば埋まるかを提案として書く(データは足さない)。

## 5. 第 2 部: 資料を作った版を足す

資料のいちばん上に `generator` を足す。

| 項目 | 中身 |
|---|---|
| `generator.name` | `ikimonobiyori` |
| `generator.version` | 版(今は 0.2.0。版を持っている 1 か所から読む。文字列を 2 か所に書かない) |
| `generator.commit` | 作業フォルダの commit(40 桁)。git が無い・読めないときは `null` |
| `generator.dirty` | 追跡中のファイルに未 commit の変更があるか。分からなければ `null` |
| `generator.generated_at` | 実際に作った時刻(時計。ISO 8601・オフセットつき)。`now`(`--now` で渡せる基準の時刻)とは別 |

- commit の読み方は、子プロセスをシェルを介さず引数の配列で起動する(今ある同じ用途のコードがあれば使う)。失敗しても資料は作る。
- **資料の id は変えない**(`generator` を id の計算に入れない)。同じ質問・同じ `now` なら、`generator.generated_at` のほかは同じ資料になること。
- テストでは、時計と commit を差し替えられるようにする(今あるテストの仕組みに合わせる)。

## 6. 第 3 部: スキーマ・確かめ・文書

1. **スキーマ**: 資料の形を決める JSON Schema は今ありません。`ikimonobiyori/schemas/` に `guide-brief.schema.json` を置き、**今回足した項目と、いちばん上の必須の項目(`schema`・`id`・`question`・`now`・`candidates`・`facts`)だけ**を決める(ほかは `additionalProperties` を許す。今ある項目を縛らない)。8 つの資料がこのスキーマを通ることをテストにする。
2. **答えが変わらないことの確かめ**: 直したあとに第 0 部の 8 つの資料を作り直し、直す前と比べる。
   - JSON: 足した項目(`place_id`・`lat`・`lon`・`coord_source`・`site_ref`・`generator`)を除いて、1 文字も違わないこと。
   - Markdown: 1 文字も違わないこと。
   - `fallback.text`: 1 文字も違わないこと。
   - 違えば、その変更を取り消す。
3. `ask verify` のテスト・提案の出力(`proposals`)のテスト・`tests/contract/` を実行する。
4. 文書: `docs/concierge-brief-fields.md`(「無い」と書いた 2.2・2.7 を直し、足した項目を表に入れる)、`README.md`・`AGENTS.md`(ビヨリコンシェルとの関係の節に、足した項目を 2〜3 行)、`CHANGELOG.md`。

関係するテストを実行して commit。
