# 段階63a 検査の作り直し：答えが必ず出る仕組み

> Claude Code への指示書（2026-11-08）。モデルは Opus。
> **この指示書は `docs\stage63-answer-always-instructions.md`（段階63）より優先します。** 両方を読み、食い違うところはこの指示書に従ってください。

## 背景

イキモノビヨリは、現在、ほぼ使えない状態です。「今日お出かけするならどこ?」と聞くと、8分以上かかって「今は答えを用意できません」と出ます。分かっている原因の例：

- 骨組みの出典に、本文で使っていない出典が残り、`source_unused` の検査と、骨組みの出典が落ちたことを見る検査が矛盾して、どちらかが必ず不合格になる
- 冒頭の文の場所が「今回のおすすめ」と食い違う
- 複数地域の答えが 1,500 字を超える
- 検査に落ちたとき、逃げ道がなく、利用者に質問するか「答えを用意できません」になる

段階55〜62で検査を足し続けた結果、検査どうしが矛盾し、1つでも落ちると答え全体が止まる作りになっています。段階63は個別の不具合を直す計画でしたが、この段階63aでは、**検査の仕組みそのもの**を作り直します。外部のレビュー（`docs\ikimonobiyori-design-review-proposal.md`）の考え方を採用します。ただし、レビューはリポジトリを読まずに書かれた提案なので、**必ず現在のコードとテストを読んでから**、実装に対応づけてください。

## 守ること

1. **事実（日付・数値・場所名・出典）は、引き続きコードが作り、コードが照合します。** フォールバックのときも、一般知識から事実を作りません。
2. **答えを止めてよいのは、危険な案内か、事実の誤りだけです。** しかも、その部分だけを外し、残りは答えます。文体・長さ・言い回しの好みで答えを不合格にしません。
3. **利用者に質問しない。「今は答えを用意できません」と答えない。** 答えの最後に質問を出さない（2026-11-07の本人指示）は、引き続き守ります。
4. 新しいライブラリを追加しません（追加には本人の承認が必要です）。PyYAML がまだ依存に入っていなければ、契約ファイルは JSON か Python で作ります。
5. 情報源の承認欄を変えません。push しません（commit まで）。
6. 実行していないテストを「通った」と書きません。実行できなかったものは「未実行」と書きます。
7. 作業ブランチ: `stage63`（なければ main から作る）。

## 第0部 検査の棚卸し（挙動は変えない）

1. 答えを作る流れ（記録 → 計画 → 骨組み → 整え → 検査）のコードと、すべての検査、関連するテストを読みます。`docs\answer-checks.md` があれば読みます（なければ、まだないと書きます）。
2. 実在する検査を、1つずつ表にします。`docs\stage63a-check-inventory.md` に書きます。

   | 検査のID | ファイル:行 | 何を見るか | 分類 | 処置 | 衝突・重複する検査 |
   |---|---|---|---|---|---|

   - 分類: 事実 / 安全 / 整合 / 出力可能 / 品質 / 表現
   - 処置: 維持 / 統合 / 警告にする / コードの自動修正にする / 生成側へ移す / 削除候補
3. 衝突・重複は、**根拠のファイルと行を示して**書きます。推測だけのものは「未確認」と書き、欠陥と断定しません。
4. 第0部が終わったら commit します（コードは変えません）。

## 第1部 答えが必ず出る（最優先）

1. 一発コマンド `ask answer`（段階63の第2部）を、次の作りにします。
   - 入力: 質問の文
   - 出力: **必ず空でない答えの本文**と、状態（`PASS` / `DEGRADED` / `BLOCKED`）
   - 本文が出たら終了コードは 0
2. フォールバックの順番（上から試し、最初に出せたものを答えにする）：
   1. 整えた文章（必須の4つの検査に合格）
   2. コードが作った骨組みの文章（整えた文章が落ちたとき）
   3. 部分回答（問題のある候補・主張を外した骨組み）
   4. 最低限の答え（確認できた範囲と、確認できなかったこと、確認の方法）
3. 整える工程の作り直しは**最大1回**。2回目も落ちたら、骨組みを答えにします（ループしない）。
4. **時間の上限**を設けます。全体で3分を目安にし、取得が時間切れになったら、保存済みの情報（キャッシュ）で答え、古い情報であることを本文に書きます。
5. 「今は答えを用意できません」という文を、コードからなくします。テストで、この文が出ないことを確かめます。

## 第2部 必須の検査を4つにする

| 必須の検査 | 見ること |
|---|---|
| 事実の照合 | 本文の日付・数値・場所名・出典が、骨組みの事実と一致する。観察の日と情報を取った日を混同しない |
| 安全 | 危険な案内がない。立入禁止・利用制限・閉館などを無視していない。不確かなことを断定していない |
| 整合 | 同じ答えの中で、日付・場所・おすすめが食い違わない（冒頭の文と「今回のおすすめ」の一致など） |
| 出力可能 | 空でない。形が壊れていない。未確認のことを未確認と書けている |

1. 第0部の表をもとに、今ある検査をこの4つに統合します。4つ以外の検査は、**合否に使いません**。
2. 品質・表現の検査は、次のどちらかにします。
   - **コードの自動修正**（直してから、もう一度4つの検査を通す）。例：
     - 出典の一覧は、コードが**本文に使った事実から**作る（`source_unused` と出典が落ちた検査の矛盾をなくす）
     - 冒頭の文の場所は、コードが「今回のおすすめ」から機械的に作る
     - 字数の上限は地域の数に応じて広げ、超えたら点数の低い候補から減らす
     - 内部用語・作業の事情の文（段階62の禁止語）は、その文をコードが削除する
   - **警告**（ログに残すだけで、答えは出す）
3. 4つ以外の検査を新しく作るときは、4つで扱えない理由と、それを捉えるテストを書いてからにします。

## 第3部 問題を局所化する

1. 検査の結果は、答え全体ではなく、**候補（場所）ごと・主張ごと**に持ちます。
2. ある候補の出典が確認できない、現況が古い、閉館している、などのときは、その候補だけを外すか「未確認」と書き、ほかの候補は残します（状態は `DEGRADED`）。
3. 危険な案内は、その部分を外すか安全な案内に置き換え、残りを答えます（状態は `BLOCKED`）。すべての候補が外れたら、最低限の答えにします。
4. 「観察の記録がある」と「今そこで見られる」は、別の主張として扱います。

## 第4部 整えた文章の照合

1. 骨組みの事実（日付・数値・場所名・出典）を、構造化したデータ（一覧）として持ちます。
2. 整えた文章から同じ事実を取り出し、骨組みと照合します。食い違ったら、**骨組みのデータが正しい**とし、骨組みの文章を答えにします。
3. 段階63の「整えた文章の一致検査の改善」は、この第4部に統合します。

## 第5部 検査のログ

1. 答えごとに、状態、4つの検査の結果、落ちた理由、警告、フォールバックの段（1〜4）、外した候補の数、かかった時間を、1行のJSONで記録します。
2. 置き場所は、リポジトリではなく、データ置き場（`C:\Users\takem\AppData\Local\ikimonobiyori\` の下の `logs\answers.jsonl`）。
3. `ask checks report`（名前は既存のコマンドの付け方に合わせる）で、よく落ちる検査、フォールバックの段の割合を表示します。

## 第6部 仕様を1か所にまとめる（Answer Contract）

1. 答えの形、必須の4つの検査、字数の上限、フォールバックの順番を、**1つの定義ファイル**にまとめます（JSON か Python。新しいライブラリは使わない）。
2. 骨組みを作るコードと、検査のコードの両方が、この定義を読みます。
3. `docs\answer-checks.md` は、この定義から自動で作ります（手で二重に管理しない）。段階63の「検査ルールの文書化」は、これに置き換えます。
4. 大きくなりすぎる場合は、第1〜5部を先に終え、第6部は途中で止めて、残りを報告に書いてください。

## 第7部 テスト

1. レビューの受け入れケース10件を、テストにします（`docs\ikimonobiyori-design-review-proposal.md` の第7節）。
2. 実際に失敗した質問を、テストにします。
   - 「今日お出かけするならどこ?」
   - 「イキモノビヨリを使って、今日お出かけするならどこ?」
   - 複数地域（例：「埼玉と神奈川で紅葉」）、複数期間（例：「今週末と来週末」）
   - 出発地つき（例：「大宮から近場で手軽に」）
   - 期待: どれも、空でない答え。「答えを用意できません」が出ない。利用者への質問がない。3分以内。
3. 段階63の骨組みの総当たり（1,000ケース）は、`ask answer` の出力に対して行い、「必ず本文が出る」ことを確かめます。
4. 既存の回帰テストで、期待値が「不合格」になっているものが、新しい仕組みで「警告」や「自動修正」になる場合は、**理由を報告に書いて**期待値を更新します。事実・安全の検査の期待値は、緩めません。

## 第8部 スキルの手順

1. ikimono-weekend のスキルの手順を、次のとおり短くします。
   - 質問を受けたら `ask answer` を1回実行し、出てきた本文を**そのまま**答えにする
   - 検査に落ちても、利用者に質問しない。コードの修正を利用者に尋ねない
   - 「今は答えを用意できません」と答えない
2. スキルの説明（description）を、お出かけ・生き物・紅葉・花・野鳥の質問で自動で起動するように見直します（段階63の第5部）。

## 第9部 段階63の残り

第1〜8部が終わったら、段階63の指示書のうち、この指示書で置き換えていない部分を行います（段階62の積み残し：行事ページの読み直し、長瀞の地点、シモバシラの時期など）。**段階63の第7部（3つの判断）は承認欄が「未」なので、実行しません。**
