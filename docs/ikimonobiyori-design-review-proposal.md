# ikimonobiyori 回答検査設計の改善提案

> Claude Code への設計レビュー・実装検討用

## 目的

質問への回答を「計画 → 骨組み（コードが生成）→ 文章の整え → 検査」の流れで作る際、検査ルールの増加や相互矛盾によって回答が出なくなる問題を防ぐ。事実（日付・数値・出典）は引き続きコードが生成し、検査で照合する。

## 確認状況と適用上の注意

**リポジトリ固有の所見は未確認である。** 参照したレビュー時点では、公開リポジトリの存在は確認できた一方、`docs/answer-checks.md` は GitHub 連携で取得できず（404）、公開ページ本文も取得できなかった。そのため、以下はユーザーが説明した工程・問題に対する設計提案であり、現行ルールの実在、特定の重複・矛盾、実装上の欠陥を確認したものではない。

Claude Code は実装に着手する前に、現在のブランチと関連コード、`docs/answer-checks.md`、テストを読み、提案を実装に対応づけること。実行結果を確認できていない段階で、テスト済み・実装済みとは扱わないこと。

## 提案の要約

1. 生成と検査が同じ仕様を参照する **Answer Contract** を導入する。
2. 検査は、事実・安全・内部整合性・出力可能性の4つの必須ゲートに整理する。
3. 品質や文体の改善は警告または生成工程に置き、回答の合否を左右させない。
4. 検査状態を `PASS` / `DEGRADED` / `BLOCKED` に分け、問題のある主張だけを局所化する。
5. 事実を構造化し、清書後も元データとの照合を行う。
6. 検査結果とフォールバック適用を記録し、ルール追加前に再発・過剰検査を分析する。

## 1. ルールの分類と、起こりうる衝突

現行ルール一覧を確認したうえで、各ルールを次の目的に分類する。

| 分類 | 目的 | 扱い |
|---|---|---|
| 事実検証 | 日付・数値・出典の正しさ | 必須ゲート |
| 安全検証 | 危険な行動や重要な制限の見落とし防止 | 必須ゲート |
| 整合性検証 | 回答内の矛盾や条件の食い違いの検出 | 必須ゲート |
| 品質検証 | 読みやすさ、説明の十分さ | 原則として警告 |
| 表現検証 | 文体、言葉遣い、構成 | 原則として生成・清書側 |

次は、実在を確認した指摘ではなく、棚卸し時に照合したい衝突パターンである。

### 情報不足と回答必須の衝突

「根拠のない情報を出さない」「具体的に回答する」「情報不足なら回答を控える」を同時に厳格適用すると、回答不能になりうる。回答全体を止めず、確認済みの情報は答え、未確認事項は未確認、不明事項は不明と明示し、推測は事実と分ける。

### 出典要件と情報源の適合性

情報源ごとに得意分野が異なるため、全ての主張に一律の出典条件を課すと、適切な根拠がある情報も排除されうる。主張の種類ごとに必要な証拠を定義する。観察記録があることと、現在その場所で観察できることは別の主張として扱う。たとえば自治体は施設の開園・イベント、ビジターセンターは現地情報、GBIF・eBird・iNaturalistはそれぞれの観察記録の根拠候補となるが、出典の適合性は個々の主張に対して判断する。

### 清書と検査の重複

清書が読みやすさを整え、検査も文体や構成を厳格に合否判定すると、修正と再検査のループを招く。清書は文章品質、検査は事実・安全・整合性を主に担う。文体の好みだけで回答を不合格にしない。

### 同一事実を別名で重複確認

日付・季節・観察時期・情報の新しさなどが別々のルールで同じデータを見ている可能性がある。ルール一覧で実際の重複を調べ、日付、対象期間、観察日、情報取得日、出典を共通のデータ構造にまとめて検証する。

ルール追加のたびに例外ルールを足して整合させる方式は避ける。個別ルールの寄せ集めではなく、共通の上位仕様を設ける。

## 2. Answer Contract による生成と検査の一本化

生成側と検査側を同じプログラムにする必要はない。両方が**同じ仕様定義**を参照することが要点である。

```text
Answer Contract（回答形式・事実要件・安全要件・不確実性の扱い）
       ├── 生成側：仕様に沿って回答データを構築
       └── 検査側：同じ仕様に照らしてデータと根拠を検証
```

実装の置き場所はリポジトリの構成を見て決める。概念例：

```text
config/answer_contract.yaml
core/answer_builder.py
core/answer_validator.py
core/fallback.py
models/facts.py
models/evidence.py
models/answer.py
docs/answer-checks.md
```

`answer_contract.yaml` を唯一の仕様定義とし、文書の `answer-checks.md` はそこから生成するか、少なくとも同じ定義への参照として保つ。手動で二重管理して再び乖離させない。YAML自体が安全性を保証するわけではない。日付・数値・出典の照合ロジックはPython側に実装する。

概念例（既存仕様を確認してから調整すること）：

```yaml
version: 1
facts:
  date: { required: true, source_required: true }
  numeric: { required: true, source_required: true }
  observation_status: { allow_unknown: true }
safety:
  dangerous_guidance: reject
  unsupported_certainty: downgrade
consistency:
  contradictory_facts: reject
output:
  always_return: true
  uncertainty_label: true
```

### 構造化した事実と根拠

文章を先に自由生成するのではなく、事実・根拠・不確実性・提案を含む構造化データを作り、コードで照合してから清書する。

```python
answer = {
    "title": "今週末の野鳥観察",
    "facts": [
        {
            "claim": "観察記録がある",
            "value": True,
            "source": "...",
            "observed_at": "...",
            "observation_date": "...",
        }
    ],
    "uncertainties": [],
    "recommendations": [],
}
```

清書後の文章を元の構造化データと照合し、コードが作った日付・数値・出典などが言い換えで変わっていないことを確認する。根拠データには、可能なら主張との対応、観察日、取得日を保持する。

## 3. 安全に必要な最小限の4つの検証ゲート

検査を次の4ゲートに集約する。実際のルールを棚卸しして、各ルールがどのリスクを防ぐかを対応づけてから移行する。

1. **事実の照合（必須）** — 日付・数値・出典が構造化データと一致する。出典が取得でき、該当主張を裏付ける。観察日と情報取得日を混同しない。
2. **安全性（必須）** — 危険な案内がない。立入禁止や利用制限など重要な制約を無視していない。不確かな情報を確実な事実として断定していない。
3. **内部整合性（必須）** — 同一回答に相反する日付・数値がない。推奨理由と根拠が食い違わない。
4. **出力可能性（必須）** — 回答形式が壊れておらず、空でない。未確認事項を未確認として表現できている。

4つ以外の独立した合否ルールは原則設けない。新設する場合は、既存ゲートで扱えないリスクと受け入れテストを明示する。

| ルールの性質 | 推奨する扱い |
|---|---|
| 同じ事実を異なる名前で検査 | 統合 |
| 表現・文体の細かな指定 | 生成・清書側へ移す |
| 情報量の最低基準 | 警告にする |
| 推奨理由の文章品質 | 生成側へ移す |
| 情報不足を理由とする全面拒否 | 廃止し、範囲を限定して回答 |
| 既存ルールの例外を救済するルール | 原則として上位仕様に統合 |
| 事実捏造や危険案内の防止 | 維持し、該当ゲートに集約 |

## 4. PASS / DEGRADED / BLOCKED とフォールバック

検査失敗と回答禁止を同一視しない。状態は回答全体の有無ではなく、回答可能な範囲と問題の種類を表す。

| 状態 | 意味 | 処理 |
|---|---|---|
| `PASS` | 必須ゲートに問題なし | 通常回答 |
| `DEGRADED` | 一部の情報が不足・未確認 | 回答範囲を限定し、不確実性を明記 |
| `BLOCKED` | 危険な主張・内容が含まれる | 問題箇所を除外または安全な形に置き換え、残りを回答 |

`BLOCKED` でも、可能な範囲で回答全体を空にしない。安全な回答が作れない場合は、確認できなかった理由と次の確認方法を説明する。

例：公園の開園情報が未確認なら、その公園を利用可能と断定せず未確認と示し、確認できた他の観察情報で回答する。

### フォールバックの優先順位

1. **通常回答** — 全必須ゲートに合格した情報を回答。
2. **部分回答** — 根拠の不足した主張・場所だけを除外し、確認済み情報で回答。
3. **保守的回答** — 推薦の断定を避け、一般情報と確認事項を案内。
4. **最低限の回答** — 確認できなかった項目、理由、判断に必要な追加確認を説明。

### フォールバックの原則

- 問題を回答全体ではなく、該当する主張・地点・情報源に局所化する。候補の一つに問題があれば、他の候補を残せるか評価する。
- フォールバックで事実を補完しない。一般知識から日付・数値・出典を創作しない。事実は引き続きコードが生成し、出典と照合する。
- フォールバック後は変更された部分に関係する検査を行い、最後に共通の安全性・出力可能性を確認する。依存関係上必要な検査は省略しない。
- 信頼度（確実性）と検査状態を別々に管理する。

## 5. 検査ログとルール追加の管理

回答ごとに、状態、各ゲートの結果、失敗理由、フォールバックの適用内容を記録する。例：

```json
{
  "answer_id": "example-001",
  "result": "DEGRADED",
  "checks": [
    { "id": "fact_consistency", "result": "PASS" },
    { "id": "safety", "result": "PASS" },
    {
      "id": "source_verification",
      "result": "UNKNOWN",
      "reason": "現地情報を確認できない"
    }
  ],
  "fallback": {
    "applied": true,
    "removed_claims": 1
  }
}
```

ログから、失敗頻度の高い検査、同一原因による回答不能、過剰に厳しい検査、フォールバックの有効性を確認する。ログの保存期間・個人情報の扱いは既存方針に従う。新しい検査ルールを追加する前に、既存ゲートで対応できないリスクなのか、受け入れテストで再発を捉えられるかを確認する。

## 6. 優先順位付き移行案

既存の実装とテストを確認し、段階ごとに挙動を比較しながら進める。

| 優先度 | 改修 | 目的 |
|---|---|---|
| P0 | 回答全体を止める失敗処理を見つけ、部分回答・安全な最低限回答に切り替える | 回答不能の解消 |
| P1 | ルールを分類し、重複・矛盾を一覧化して統合 | ルールの整理 |
| P2 | Answer Contract を導入し、生成と検査を共通仕様に接続 | 仕様の一元化 |
| P3 | 事実・根拠を構造化し、清書後も照合 | 事実の改変防止 |
| P4 | 検査ログと失敗分析を導入 | 再発防止と調整 |

一度に全面置換せず、現行ルールから新ゲートへの対応表とテストを用意して移す。ドキュメントが実装と別々に更新されない仕組みも作る。

## 7. 受け入れテストケース

次のケースについて、期待状態・回答内容・除外した主張・ログを確認する。既存テストの規約に合わせて具体化する。

| ケース | 期待する結果 |
|---|---|
| 必要な情報と根拠が全て確認できる | `PASS` の通常回答 |
| 複数地点のうち1地点だけ出典を確認できない | `DEGRADED`。その地点だけ除外または未確認とし、他の有効な地点は回答 |
| 日付の根拠が不足している | 日付を断定せず、確認済みの範囲を回答 |
| 数値が出典と一致しない | 不一致の数値を事実として採用せず、問題を記録して安全に回答 |
| 出典を取得できない | 未確認と明示し、根拠のない主張を外して回答 |
| 一部に危険な案内が含まれる | 該当部分を除外または安全な案内に置換し、残りを回答 |
| 清書段階で数値・日付が変わる | 事実照合で検出し、構造化データを正とする |
| 全候補が利用できない、または確認できない | 空回答にせず、確認できなかった理由と次の確認方法を案内 |
| 情報源の記録はあるが、現在の観察可能性までは示さない | 記録の存在と現在の観察可能性を区別して表現 |
| 表現や説明量の改善が必要だが必須ゲートには問題がない | 警告または清書上の改善にとどめ、回答を不合格にしない |

## 8. 設計原則

1. **事実はコードが担保する。** 日付・数値・出典は構造化データとして生成し、検査で照合する。
2. **仕様は一元管理する。** 生成と検査が別々の正しさを定義しない。
3. **検査は安全性を優先する。** 文体の好みや品質改善だけで回答を止めない。
4. **不確実性を隠さない。** 不明は不明とし、推測を事実に変えない。
5. **確認できる範囲で答える。** 情報不足は回答範囲の限定に反映し、全面拒否を避ける。

設計の中心は「正しい情報だけを使って、分かる範囲を最大限回答する」ことである。

## Claude Code への作業依頼

まず関連コード、`docs/answer-checks.md`、既存テストを調査し、実在する各検査ルールを「維持・統合・警告化・生成側へ移動・削除候補」に分類してください。ルール間の衝突と重複は、根拠となるファイル・箇所とともに表にしてください。未確認の仮説を実装上の欠陥として断定しないでください。

その調査結果を踏まえて、Answer Contract と4つのゲート、状態遷移、フォールバック、構造化事実、ログへの移行案を提示し、段階ごとに実装してください。事実（日付・数値・出典）はコードが生成し検査で照合する方針を保ってください。上記受け入れケースをテストに加え、実行可能な環境では実行結果を報告してください。実行できない場合は未実行と明記し、成功したと主張しないでください。
