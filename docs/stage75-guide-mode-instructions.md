## 0. 目的と方針

### 0.1 なぜ作るか

イキモノビヨリの目的は、観光案内の検索ではなく、**ネイチャーガイドの知識を AI にすること**。ところが今は、コードが答えの文章を作り、AI はそれを運ぶだけになっている。そのため「今週末の紅葉の情報は?」のような簡単な質問で、イキモノビヨリを使わないふつうの Claude のほうが、よい答えを出すことがある。

この段階では、役割を逆にした形を**試作**する。

- **AI が、ガイドとして答えを書く**（なぜ今それが見られるのか、どこをどう見るのか、周りの生き物とのつながり）。
- **コードは、腐りやすい事実だけを記録と照らす**（今年の現況・日付・行事の期間・開園時間・料金・電話・通行止め・範囲外の地名）。
- コードは、AI に渡す**「ガイドの資料」**（候補と順位・確かめた事実・知識カード・決まり）を作る。

### 0.2 変えないもの

- **今の `ask answer` は消さない・挙動を変えない**。単体で使う形（コードだけで、毎回同じ答え）として残す。新しい形は、横に別の経路として足す。
- 既定の動きは今のまま。新しい形に切り替えるかどうかは、本人が比較を読んで決める（設定で切り替えられるようにするだけ。第3部）。
- 記録・知識カード・名所カタログ・台帳・キャッシュ・写真は、そのまま材料として使う。

### 0.3 共通の決まり

- 段階64の指示書の「0」と同じ: 全テストは4分割で実行し、件数が一致・すべて OK で commit／push しない／本人に質問しない／承認の記入をしない／破壊的操作をしない。
- 事実の決まりも今までと同じ: ウェザーニュース（転載を含む）・tenki.jp・日本気象協会の予想・SNS は使わない／山と溪谷オンラインは状態の語・日付・URL のみ／承認待ちの情報源は答えに使わない／行事の期間を例年の見頃にしない／範囲は横浜から250km前後／内部の言葉・作業の事情を答えに出さない／答えの最後に質問を出さない。
- **試作である**。10問が通ることを優先し、作り込みすぎない。迷った設計は、単純なほうを選び、報告書の「判断したこと」に1行書く。
- **時間の上限: 開始から6時間**。過ぎたら区切りのよいところで止め、進捗・報告書を書いて commit して終了する。
- **通信の上限**: コードからの取得は合計300回（直列・同じホストへは1秒以上あける・robots.txt で拒否されたページは取得しない）。最初に `ask warm` を1回実行する。
- 使用上限やコンテキストの圧縮で止まりそうなときは、先に進捗ファイルを更新する。再開は、本人が同じ依頼を貼る。
- 報告・進捗・commit メッセージは日本語。

## 1. 第1部: ガイドの資料を作る（`ask brief`）

新しいコマンド `ask brief "<質問>"` を作る。今の計画（ask plan）の結果を使い、AI に渡す資料を1つのファイルにまとめる。骨組み（skeleton）と整え（polish）は通さない。

1. 引数は `ask answer` に合わせる（出発地・日付など）。加えて `--prev <資料のid>`（続けて聞く質問で、前の質問の資料を引き継ぐ）。
2. 出力は、データ置き場の `briefs\<id>.json` と、同じ内容を人が読める形にした `briefs\<id>.md`。標準出力には id とパスだけを出す。
3. 資料に入れるもの:
   - **質問と日付**: 質問の文、今日の日付、「今週末」「来週末」が指す実際の日付、質問の型、範囲（scope）、出発地。
   - **候補と順位**: 今の計画が選んだ候補と順位、選んだ理由（距離・今年の現況の有無・地域の偏りの調整など）。
   - **確かめた事実**（1件ごとに id `F001`…）: 種類（今年の現況／例年の目安／行事／施設／安全・規制）、内容、値（日付・時刻・料金・状態の語など、照らす対象になる値を項目として分けて持つ）、出典の名前、発行元の区分（公式／その他）、URL、観測日、取得日。
   - **知識カード**（id `K…`）: 質問の場所・種・山に結びつくカード。
   - **足りないもの**: この質問について、記録にないこと（例: 「霞ヶ浦の野鳥の記録は2件だけ」「今年の現況がない」）。AI が正直に書くための材料。
   - **決まり**: 0.3 の事実の決まりを短く。
4. 承認待ちの情報源の事実は、資料に入れない。
5. 同じ質問・同じ日付・同じキャッシュなら、同じ資料になること（決定的）。テストを足す。

## 2. 第2部: 書き方の手本（docs\guide-voice.md）

AI がガイドとして書くための手本を、**8,000バイト以内**で作る。CLAUDE.md・SKILL.md には全文を入れず、参照だけを足す（SKILL.md の上限15,000バイトを守る）。

入れること:

1. **ガイドの語り**: 名所の一覧ではなく、次のことを語る。
   - なぜ今それが見られるのか（気温・標高・日当たり・渡り・植物の暮らし方）。
   - 現地でどこをどう見るか（見分け方、時間帯、歩く向き、足元・水辺・梢のどこを見るか）。
   - 周りの生き物や地形とのつながり、次の季節に何が起きるか。
   - 質問に先に答える。知識の質問は、知識が先、場所は後。
2. **確かさの3段**。読む人が見分けられるように書く。
   - **公式で確認**（日付つき）: 資料の事実（公式）にあること。
   - **例年の目安**: 資料の事実・カードにある、例年の時期。
   - **一般的な知識**: AI の知識。種や環境についての一般的な説明に限る。
   - 表し方は、読みやすさを優先して決めてよい（例: 文中で「◯月◯日時点、△△公園の発表では」「例年は」と書き分け、最後に確かめた出典を日付つきで並べる）。記号だらけにしない。
3. **AI が自分の知識で書いてはいけないもの**（資料にあるときだけ書ける）: 今年の現況、具体的な日付、行事の名前と期間、開園時間・休園日、料金、電話、交通の規制・通行止め、**特定の名所の例年の時期**。資料にないときは「今年の状況は確かめられていません」のように正直に書くか、書かない。
4. **記録にない場所の名前**: 一般に知られた名所を AI の知識で添えてよいのは、1つの答えに3か所まで。範囲内の都県であること、「確かめていない」と分かる書き方をすること。
5. **手本**（本人が賛成した文）:
   > **氷の花（氷華）**と呼ばれます。高尾山では、シモバシラというシソ科の植物の枯れた茎にできるので、その名前で呼ばれることもあります（地面にできる霜柱とは別のものです）。

   名前を聞かれたら、まず**聞かれた現象の名前**を答える。植物の説明にすり替えない。
6. 長さの目安は、1つの答えで400〜900字。最後に質問を出さない。内部の言葉（資料・カード・記録・検査・id など）を出さない。

## 3. 第3部: 裏を取る（`ask verify`）

新しいコマンド `ask verify <答えのファイル> --brief <資料のid>` を作る。AI が書いた答えを、資料と照らす。**この部分は決定的なコードにし、テストを厚くする。**

### 3.1 答えの下書きの形

AI は、答えの下書きに次の印をつけて書く。`ask verify` が照らしたあと、印を取り除いて最終の文にする。

- 腐りやすい事実を含む文の終わりに、根拠の印をつける: `[F012]`（確かめた事実）、`[K034]`（知識カード）。
- 下書きの最後に、答えに出した**場所の名前の一覧**を書く（記録にある場所／AI の知識で添えた場所、を分ける）。

印の形は、実装しやすいように変えてよい（報告書に書く）。

### 3.2 照らす内容

1. **印のある文**: 印の id が資料にあること。その文の中の日付・時刻・料金・電話・状態の語（見頃・色づき始め・落葉 など）・行事の名前と期間が、その事実の値と合っていること。「今年の現況」として書いた文の根拠が、種類「例年の目安」「行事」の事実ではないこと（行事の期間を見頃にしない）。
2. **印のない文**: 次のものが入っていたら不合格にする。
   - 年月日・月日、時刻、金額、電話番号、URL。
   - 「今」「現在」「今年」「今週末」などと一緒に使われた状態の語。
   - 行事を表す語（まつり・開催・ライトアップ など）と期間。
   - 通行止め・閉鎖・規制。
   - 記録にある場所の名前と、月の表現が同じ文にあるもの（特定の名所の例年の時期）。
   - 例外: 種や環境についての一般的な季節の説明（「冬鳥は秋に渡ってきます」のように、場所の名前を含まない月・季節の表現）は合格。
3. **場所の名前**: 一覧の名前が、名所カタログ・エリア辞書・山（sites.yaml）・未確認の名所のどれかにあり、範囲内であること。AI の知識で添えた場所は、3か所以内・範囲内の都県・「確かめていない」と分かる書き方であること。添えた場所は、今ある `ask record-unverified` で記録する（あとで公式ページで確かめる材料にする）。
4. **今までの検査の再利用**: 使わない情報源の名前、内部の言葉、最後の質問、範囲外の地名、質問の場所のすり替え（聞かれた場所と違う場所の話になっていないか）は、今ある検査（4つの検査・final_check）の部品をそのまま使う。
5. 文面の細かい決まり（骨組み用の言い回しの検査）は、新しい形には当てない。

### 3.3 結果

- 合格: 印を取り除き、最後に「確かめた出典（名前・日付・公式かどうか）」を並べた最終の文を出す。logs\answers.jsonl に、形（guide）・資料の id・照らした件数・書き直しの回数を記録する。
- 不合格: どの文が・なぜだめかを、直し方が分かる形で出す（内部の言葉は、この出力には出てよい。答えの文には出さない）。
- **書き直しは2回まで**。3回目も不合格なら、今の `ask answer` の答えを出す（必ず答えが出る、を守る）。

### 3.4 切り替えと、送る前の検査

- data\ask の設定に、答えの形の切り替え（今までの形／新しい形）を足す。**既定は今までの形**。
- `ask final-check` と Stop フックが、新しい形で合格した答え（`ask verify` が出した最終の文）を、正しい答えとして受け入れるようにする。受け入れるのは、最終の文と一致するときだけ。
- 新しい形の手順（`ask brief` → 書く → `ask verify` → 合格した文だけを出す）を、docs\guide-mode.md に書く。Claude Code 用（フックで強制）と、フックのない環境用（手順として必ず `ask verify` を通す）の両方を書く。リポジトリに AGENTS.md があれば、docs\guide-mode.md への参照を1〜2行足す（なければ作らない）。

### 5.2 報告書（docs\stage75-report.md）

1. 採点の表（10問×A/B/C）。

3. `ask verify` が止めたもの（AI が書こうとして、裏が取れずに直した記述）の一覧。**これが、新しい形の裏取りが働いた証拠になる**。逆に、止めすぎて答えが痩せた例も書く。

### 5.3 最後に

全テスト（4分割）と回帰テストが通ったら commit する。push はしない。
