## 5. 第 2 部: 原因を調べる(書くだけ。コードを変えない)

`docs/mountain-named-report.md` の最初の章として、実装の前に書く。

1. B 組の 26 の資料で、質問ごとに次を表にする: 質問の意図(`intent`)・答えの経路(`route`)・範囲の決め方(`scope`)・`region`・`areas`・候補の件数・**その山の名所(結びつきのある件)が候補にあるか**・あれば順位と `basis`。
2. **高尾山では出て、筑波山・御岳山では出ない理由**を、コードとデータで突き止める。見る所の例(決めつけない): 質問から場所を読み取る辞書・エリアの定義・山域の質問の扱い(`_area_plan`)・名所の別名・候補の数の上限・出発地からの距離の上限・対象(紅葉・花)の絞り込み・名所の承認の状態。
3. 原因を、山ごとに次のどれかに分ける。
   - **(ア) データの不足**: 場所を読み取る辞書・エリアの定義などに、その山の名前(`data/sites.yaml` の名前そのもの)が無い。
   - **(イ) 結びつきが使われていない**: 山の名前は読み取れているが、その山の名所(前回足した結びつき)を候補に入れる道が無い。
   - **(ウ) 選び方・順位の決まり**: 候補にはなるが、距離の上限・件数の上限・点数で落ちている。
   - **(エ) そもそも名所のデータが無い・対象が違う**(例: 紅葉の名所はあるが花の名所は無い)。
4. 高尾山がなぜ出るのか(どの道を通っているか)も書く。

## 6. 第 3 部: 直す(原因の種類で、やる・やらないを分ける)

| 原因 | やること |
|---|---|
| (ア) データの不足 | **直す。** 足してよいのは、`data/sites.yaml` にある山の名前そのものを、今ある辞書・定義の、今ある形の行として足すことだけ。対象は結びつきのある 6 つの山。別名・読み・範囲の広い地名(「奥多摩」など)は足さない |
| (イ) 結びつきが使われていない | **直す。** 質問から読み取った山(`data/sites.yaml` の件)と、名所の結びつき(名所カタログの `site_ref: yamabiyori:mNNN`・観察の名所の `mountain_site_ref`・`catalog_ref` 先の件の結びつき)が同じ ID のとき、その名所を候補に入れる。**今ある候補は外さない・今ある候補どうしの順位は変えない。** 入れた候補の `basis`・`rank` などは、今ある候補の種類の中でいちばん近い形に合わせ、「山の名前から入れた」ことが分かる印を 1 つ足す(名前と意味を `docs/concierge-brief-fields.md` に書く) |
| (ウ) 選び方・順位の決まり | **直さない。** どの決まりで落ちているかと、直すならどう変わるか(ほかの質問への影響を含む)を、案として報告書に書く |
| (エ) 名所のデータが無い | **直さない。** どの山のどの対象に名所が無いかを一覧にする |

直すときの決まり:

- 入れる名所が、質問の対象(紅葉・花)と合わないときは入れない(「○○の花の見どころ」に紅葉の名所を入れない)。対象を絞らない質問(「○○の見どころを教えて」)の扱いは、今の高尾山の動きに合わせる。
- 現況・例年の時期・出典は、その名所に今あるデータのとおり(無ければ、無いときの今の形のまま。作らない)。季節の外の名所を「見頃」と書かせない(見込みの語は今の決まりが決める)。
- 資料の Markdown・`fallback.text` に入れた名所がどう出るかは、今ある候補と同じ作りに任せる(特別な文を足さない)。
- 設定で切れるようにする(`data/ask/guide_mode.yaml` に 1 つ。切ったら直す前と同じ資料になること)。
