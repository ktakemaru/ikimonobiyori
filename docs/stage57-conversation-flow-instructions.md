## 2. 第1部（最優先）: 未対応のテーマを黙って別のページにしない

1. `guide page --theme <テーマ>` と `ask page` は、**対応していないテーマ・対象のとき、別のページを作らず、明確なエラーで終了**する（終了コードは0以外。メッセージ: 「このテーマの写真つきページは未対応です。対応: 野鳥、野草、…」）。
2. 対応テーマの一覧を1か所（設定または定数）に持ち、`guide page --list-themes` で見られるようにする。
3. 「該当がないときの既定が野鳥」という分岐があれば、取り除く。
4. スキル ikimono-weekend の「写真つきページ」の手順に、**エラーのとき、手書きの HTML・図で代用しない**こと、ユーザーには「今は○○の写真つきページに対応していません」と短く伝えることを書く。
5. **できないことを提案しない（本人の指摘 2026-11-07。最優先の規則）**: 「写真つきのページにもできます」「写真つきで紹介しましょうか」のように、答えの末尾などで**ユーザーに提案する文**は、**実際にできることだけ**を出す。「提案したのに、できませんでした」という流れを作らない。
   - **提案の一覧をコードで持つ**（設定ファイルに、提案の ID・文面・実行できる条件を書く。例: 「写真つきページ」→ 対象のテーマが対応済みで、直前の計画があり、必要なデータ（写真の候補）が揃っていること）。答えの末尾の提案の行は、**この一覧から、条件を満たすものだけ**を、コードが組み立てて付ける。エージェントが自由な文で提案を書き足さない。
   - 条件を満たす提案が1つもないときは、**提案の行を出さない**。
   - 検査器（ask verify）に、提案らしい文（「しましょうか」「にもできます」「お作りします」「公開できます」「作れます」「Artifact にします」など）が、**一覧にない、または条件を満たさないのに**含まれていたら不合格にする規則を足す。
   - ユーザーが頼んだことが、今はできないときは、**1行で「今は○○には対応していません」と伝え**、**確実にできる別のこと**（条件を満たす提案）だけを、1つ添えてよい。できるか分からないことは添えない。
   - CLAUDE.md・AGENTS.md・スキルに、この規則を書く。
6. テストを足す（通信なし）: 未対応テーマのとき、提案の行が出ないこと／対応済みで条件を満たすとき、提案の行が出ること／自由な文の提案が検査で不合格になること／できないことを頼まれたとき、1行の案内と、条件を満たす別の提案だけが出ること。
5. テストを足す（通信なし）: 未対応テーマがエラーになること、野鳥のページが誤って作られないこと。

## 3. 第2部（承認が「あり」のときだけ実行）: 紅葉・花・総合の写真つきページ

### 3-1. 直前の答えを引き継ぐ（`ask page`）

- 答えを書くとき（`ask plan`）の計画を、**リポジトリ外のデータ置き場**（IKIMONOBIYORI_DATA_DIR など既存の仕組み）に `last_plan.json` として保存する（対象、対象日、採用と各節、使った事実と出典。有効期間は24時間）。
- `ask page`（または「写真つきのページにして」への手順）は、**直前の計画から**ページを作る。計画がない・古いときは、「先に質問してください」と案内して終了する（別の内容を作らない）。

### 3-2. ページの構成

- 冒頭: 答えの冒頭の文と、「今回のおすすめ」3件。
- 狙い別の節。各採用に、現況（状態の語・日付・出典）、見込み、まつり期間（**別の行**）、実用情報（読めた公式の範囲）、出典。
- 写真（SVG・手書き図は使わない。既存の写真の仕組み: ライセンスの許可リスト、撮影者・ライセンス・学名・状態の表示、種ごとのキャッシュ、確認なしの自動取得）:
  - **紅葉**: 各地点の**樹種**の写真（イロハモミジ・イチョウ・ケヤキ・メタセコイアなど、カタログの樹種データから）。**地点そのものの写真は使わない**（権利と手間のため。段階53の決定）。樹種が不明な地点は、写真なし。
  - **花**: 花の種の写真（開花優先、段階53の規則）。
  - **野鳥**: 現況の種名の鳥の写真。
  - **総合**: 紅葉・花・野鳥を節に分けて載せる。
- ページ全体は2MBの目安。収まらなければ1ページの種数を減らす。公開は既存の手順（Artifact、非公開）。

### 3-3. 受け入れ条件

- 「明日の紅葉」→「写真つきのページにして」で、**直前の答えと同じ3件・同じ節**の紅葉ページができる。
- 「明日楽しめる花や野鳥を写真付きページで」で、花と野鳥の**両方**が載るページができる。
- テストを足す（合成データ、通信なし）: 計画の保存と24時間の有効期間、計画がないときの案内、テーマ別のページの構成、地点写真を使わないこと。

## 4. 第3部: 複数対象（花と野鳥など）の答え

1. 「花や野鳥」のように複数の対象を聞かれたとき、`ask plan` を**対象ごとに**作り、答えは**対象別の節**（花／野鳥／紅葉）に分けて、それぞれに「今回のおすすめ」を置く。
2. 検査器（ask verify）の「今回のおすすめ」の数え方と、冒頭の文の照合（lead_mismatch）を、**対象別の節**に対応させる。対象ごとに、おすすめの数・冒頭との整合・出典との対応を検査する。
3. 検査が不合格のまま答えを出す場合の見せ方を、整える（答えの本文に作業の事情を書かない。必要なら末尾に「一部の確認が済んでいません」の1行だけ）。ただし、この対応で、**複数対象の答えが検査に合格する**ことを目標とする。
4. 合成データでテストを足す（通信なし）: 花＋野鳥、紅葉＋花、3対象の答えが検査に通ること。対象ごとの食い違いが検出されること。

## 5. 第4部: 文面の不具合の修正

1. **記号を語にする**: 日光市観光協会の状態の記号（✕＝まだ、△＝色づき始め、〇＝見ごろ、◎＝真っ盛り、▼＝色褪せ・落葉始め。ページ上の凡例が出どころ）を、答えには**語**で出す（「△」「◎」をそのまま出さない）。凡例が読めなかった記号は、記号のまま出さず、「状態の表示あり（記号）」とせず、状態を断定しない。
2. **対象日でない日付の実用情報**: 「明日」の質問に「11/6の有料エリア 9:30〜21:00」のように前日の開園時間を出さない。開園時間は、取得日と対象日が違う場合は、「当日の開園情報は公式ページで確認」にする（通常の開園時間・休園日は出してよい）。
3. **矛盾する文**: 現況（確認種数、記録）があるのに「この時期に見られる鳥の記録は見つかっていません」と書かない。現況の有無で、文を出し分ける。
4. **現況のない候補の扱い**: 野鳥で、現況（公式の観察記録）のない公園を、おすすめの2番目に選ばない（plan の点数で、現況なしを大きく減点する）。選ぶ場合は、「公式の最近の観察記録は確認できていません」と明記し、季節の目安だけであることを書く。
5. **「例年の時期は分かりません」**: 陣馬山・京成バラ園など、例年の見頃を取得して確認できるものを補う。確認できなければ補わず、報告書に列挙する（推測で入れない）。まつり期間を例年の見頃として使わない規則は維持。
6. 各修正に、合成データのテストを足す。

## 6. 第5部: 追質問への対応（スムーズな会話）

1. 答えのあとの追質問（「もっと近場で」「山歩きで」「遠出でもいい」「ライトアップがいい」など）は、**同日の記録と計画を再利用**して、通信なしで、計画の狙い・距離の条件を変えて選び直す（`ask plan --refine`）。再取得が必要なのは、記録がない・古いときだけ。
2. 選び直した答えも、検査を通す。計画の保存（last_plan.json）を更新する。
3. 同じ日の同じ URL を、繰り返し取得しない（同日キャッシュ）。取得の待ち時間が長くなる原因（毎回3ページ以上の取得）を、報告書に書く。
4. テストを足す（通信なし）。

## 7-3. 第9部: 通常の手順を常に通す（別 commit）

背景: 「ファイルは変更せず、質問への回答だけをしてください」と言われたとき、エージェントは、取得・計画・検査を省き、「今日この会話で読んだ情報だけで答えます」「今回は新しく取りに行っていません」と、手での答えを書いた。形（今回のおすすめ、出典、確かさの補足）が崩れ、検査も通っていない。

1. **「ファイルは変更しない」は、「リポジトリのファイルを変更しない」と解釈する。** 記録・計画・キャッシュ・検査・取得は、リポジトリの外のデータ置き場（IKIMONOBIYORI_DATA_DIR など、既存の仕組み）に書いて、**通常どおり行う**。スキル ikimono-weekend・CLAUDE.md・AGENTS.md に明記する。

確認する点: 答えとページが一致／複数対象が検査に合格／記号がそのまま出ない／前日の開園時間が出ない／矛盾する文が出ない／現況のない野鳥の公園が上位にならない／作業の事情・内部用語が出ない／出典が本文と対応。
