### 2.2 利用条件
- 「You may only use the free API services for non-commercial purposes.」非商用の定義は Creative Commons の解釈による。例: 購読・広告のない個人・非営利のサイトやアプリ、個人のホームオートメーション、公的機関の公開研究、教育。
- 無料枠の上限: **600 calls/分、5,000 calls/時、10,000 calls/日、300,000 calls/月**(pricing によれば月の上限は現在は強制していない)。上限は IP アドレスとアプリケーションごと。濫用は予告なく遮断されうる。
- 「The data obtained through the API is provided under the terms of the CC-BY 4.0 licence.」
- キャッシュ・保存・再配布・加工データの公開について、無料枠の規約には記述がなかった(禁止の記述もない)。
- 規約の日付の記載なし(© 2022-2026、変更履歴は GitHub)。
- **1 call の数え方**(pricing の FAQ): 「Typically, one API call corresponds to one HTTP API request.」ただし「Requests for data covering more than 10 weather variables」または「extending over a period of more than 2 weeks for a single location are considered multiple API calls」で、端数で数える(例: 2 週・15 変数で 1.5 call、4 週で 3.0 call)。
  → **長い期間の過去データの問い合わせは 1 リクエストでも複数 call と数えられる**。正確な式は書かれていない(例から `変数の数/10 × 週数/2` に近いと読めるが**推測**。1 変数のときの下限が 1 かどうかも未確認)。見積もりは `docs/validation-plan.md` で安全側に計算する。

### 2.3 出典表示
- 既存(README): *Weather data by Open-Meteo.com (https://open-meteo.com/), licensed under CC BY 4.0*。
- 過去データ(Historical API)の仕様ページには、追加で「Generated using Copernicus Climate Change Service information 2022.」の表示が求められている(ERA5 などの再解析データの帰属)。引用例: Zippenfenig, P. (2023). Open-Meteo.com Weather API. Zenodo. https://doi.org/10.5281/ZENODO.7970649。ERA5・ERA5-Land にも個別の引用がある(文言は仕様ページで**要目視**)。
- → 段階14 で過去データを使った結果を公開するときは、上の2つを両方書く。

### 2.4 標高(`elevation`)の扱い(段階14 の前提)
- 仕様(Historical API。予報 API にも同じ引数がある想定だが、**予報 API のページは今回読んでいない = 未確認**): 「Per default, a 90 meter digital elevation model is used.」標高は統計的ダウンスケーリングに使われる。手で指定でき(例: 山頂に合わせる)、複数地点はカンマ区切り。「If &elevation=nan is specified, downscaling will be disabled and the API uses the average grid-cell height.」
- v0 は `elevation` を渡していない(`docs/stage13-report.md` フェーズ 0-4)。したがって v0 の気温は、Open-Meteo が 90 m の標高データから決めた、問い合わせ座標付近の標高のもの(応答の `elevation`: 高尾山 598 m、谷川岳 1920 m、赤岳 2599 m)。
- エンドポイント: `https://archive-api.open-meteo.com/v1/archive`。`latitude`・`longitude`・`start_date`・`end_date`(yyyy-mm-dd)が必須。日別の変数を使うときは `timezone` が必須。`temperature_2m_min` は日別で使える。
- 再解析のモデル: 既定は「Best match」(IFS HRES・ERA5・ERA5-Land を組み合わせる)。ERA5 は 1940年〜(0.25°、約 25 km、5 日遅れ)、ERA5-Land は 1950年〜(0.1°、約 11 km、5 日遅れ)、ECMWF IFS は 2017年〜(9 km、遅れなし)。モデルを選ぶ引数名はページから読み取れなかった。
- **モデルの固定(2026-10-21、ユーザーの確認)**: `models` 引数(例 `models=era5_land`)を使う見込み。**値の名前は段階14 の最初の 1 リクエストで確認する**(応答が想定と違えば止める)。答え合わせは `models=era5_land` で固定する(`docs/validation-plan.md` §0)。

- 上の 2 ページは Claude Code からは読めなかった(HTTP 403)。**ユーザーが確認した内容(2026-10-21)**:
  - 投稿(観察記録・写真)の既定ライセンスは **CC BY-NC**。
  - 規約の**第7条**は、iNaturalist のデータを **AI の学習に使うことを禁じる**。
  - API の目安: **約 1 リクエスト/秒・約 1 万リクエスト/日**。**User-Agent の設定を推奨**。
- **ikimono の使い方との照合: 適合**(ユーザーの判断として記録)。
  - 保存・出力するのは集計値(種ごとの件数と分類名)だけで、写真・観察者・正確な座標は保存しない。
  - **学習に使わない**(モデルの学習・微調整のデータにしない)。提案の材料として集計値を窓口に渡すのは、学習ではない利用と扱う(この線引きはユーザーの確認の範囲での理解。規約の原文は Claude Code は読んでいない)。
  - リクエストの間隔: `ikimonobiyori/config.yaml` の `live.min_interval_s: 2`(0.5 リクエスト/秒以下)。1 日の上限: ハブの `host_daily_caps` の `api.inaturalist.org: 1000`(目安の 1/10)。どちらも目安の内側。
  - **User-Agent(コードは変えていない。調べた結果)**: iNaturalist への取得はすべて User-Agent を付けている。値は `ikimonobiyori/config.yaml:25` の `live.user_agent` = `biyori-hub/ikimonobiyori (personal, non-commercial)`。
    - 野鳥の取得 `ikimonobiyori/fetch/birds_live.py:116` → `fetch/live.py:31-32` の `default_http_get`(urllib の `Request(url, headers={"User-Agent": user_agent})`)。
    - 野鳥の調査 `ikimonobiyori/survey.py:92` → 同じ `default_http_get`。
    - (参考)紅葉(Open-Meteo)は `fetch/live.py:45-46,58,176` の `SessionGetter`(requests の Session に同じ User-Agent)。
    - 連絡先(メールアドレスや URL)は User-Agent に入っていない。入れるかは決めていない(個人の連絡先を外部に送ることになるため、入れるならユーザーが決める)。
- 変えないこと: 実際の応答をリポジトリに置かない(テストは合成データ)、野鳥の実通信を増やさない、用途は個人・非商用の下調べ。
- **CLAUDE.md・AGENTS.md の規則 6 は段階17 で「ユーザー確認済み(2026-10-21)」に直した**(指示書 段階17 フェーズ3 の 4。実通信の制限は変えていない)。**README にはまだ「まだ人の目で確認していません」と書いてある**。この文言はテスト `test_license_is_mit_and_readme_states_the_terms` が検査しており、テストの期待値を変えるにはユーザーの確認が要る(CLAUDE.md 完了条件 2)ので、段階17 では変えていない(`docs/stage17-decisions.md`)。

## 7. 現地の情報を主にする(段階15。2026-10-23 決定、ユーザー承認)

`docs/design.md` §0 の決定のうち、データ源の扱いに関わるもの。

### 7.1 情報の種類
| 種類 | 例 | 紅葉での使い方 |
|---|---|---|
| ① 現地の現況発信 | 観光協会・自治体・公園の管理者の公式な「紅葉状況」ページ | **主**。名所ごとの公式の状態と更新日 |
| ② 自治体のオープンデータ | 自治体標準オープンデータセットの観光施設一覧・イベント一覧 | 段階15 では使わない(次の段階の提案) |
| ③ 市民の観察記録 | iNaturalist など | 紅葉では使わない |
| ④ 公的な観測 | 気象庁 生物季節観測(§1) | 名所カタログの例年の時期とともに、候補の絞り込み |

### 7.2 読み方と残し方
- **答えるときにエージェントが読む**のはよい。これまでの「自動収集しない」は、**定期的な巡回・本文の保存をしない**という意味に読み替える。
- 読み取りのコード(スクレイピング)は書かない。読むのはエージェント(Claude Code / Codex)の道具。
- 残してよいのは読んだ結果の**事実だけ**: 情報源 ID、名所、公式の状態(原文の記号・語と共通の段階)、公式の更新日、読んだ日時、URL。本文の写し・写真は残さない。置き場所は git の追跡外(`IKIMONOBIYORI_DATA_DIR` の下の `status_log/<subject>.jsonl`)。
- 自動アクセスを拒否しているサイト(robots.txt や応答で拒否されたもの)は読まない。台帳に `readable.status: refused` と記録し、人が開く前提の URL として扱う。

### 7.3 情報源にする条件と承認
- 発信者が観光協会・自治体・公園の管理者などの**公式**であること。まとめサイト・旅行予約サイト・天気会社・個人ブログは使わない。
- 仮承認(段階15、ユーザー不在のため): 公式・実際に読めた・利用条件が要約や出典つきの事実の利用を禁じていない、の**すべて**を満たすものを `approval.status: approved`、`approved_by: claude_code_provisional` にした。ユーザーが見直して取り消せる(`docs/stage15-review.md`)。
- ユーザーの見直し(2026-10-23): 承認済み 13 件をユーザーの承認(`approved_by: user`)に切り替えた。伊勢原市の大山のページは現況の情報源にせず pending(例年の時期の参考)。年のない更新日(箱根町観光協会)は「新しさ不明」として扱う。記録は `docs/stage15-decisions.md` D-34〜D-40。
