## 1. 共通の決まり（これまでの本人の決定。変えない）

- 情報収集のための通信は承認なしで行ってよい。確認を求めない。写真の取得も確認なし（自動）。
- 「公式かどうか」は答えの条件ではなく**確度のラベル**。公式でない情報（紹介サイト等）も日付・出典つきで通常の候補に使い、「公式ではありません」と添えるだけにする。「公式情報がないので答えません」にはしない。
- 「情報が古いから答えない」はしない。古い情報は日付つきの参考として出す。
- tenki.jp は読む対象から外す（取得済みの値も答えの材料にしない）。ウェザーニュースは読まない。
- 場所の指示がない質問は、登録済みの全範囲（横浜から片道250km前後）で答える。
- Artifact/HTML を求められたら写真つきページを標準にする（イラスト版にしない）。
- 答えに内部用語（guide find、record-candidate、policy.yaml、reader: code、作業メモ等）、「検査に合格」「テスト未実行」「記録が1件増えた」を出さない。使う人には「何月何日時点」だけ示す。
- 新しいライブラリは足さない。
- 作業中は関係するテストだけ実行し、全テストは CI に任せる（段階46で約6.5分に短縮済み）。
- 完了後は push → PR 作成 → CI 全項目 pass を確認 → main にマージまで自分で進める。CI が赤ならマージせず原因を報告書に書く。

## 2. 第1部: 答えの作り方の改善（最優先・別 commit）

背景: 「今週末に紅葉を見に行きたい」に、ネイチャーガイドとして直接答えた回答のほうが、イキモノビヨリの答えより魅力的だった（本人評価、2026-11-05）。その差を取り入れる。

直接回答の特徴（取り入れる要素）:
- 事実（今どの段階か・日付・出典）＋ 今週末の見込み ＋ 実用情報（アクセス、混雑、駐車場、見どころ）が1つの文章にまとまっている。
- 狙い別の構成（例: 近場で手軽に／絶景を狙う／ドライブ／歩いて楽しむ）で、読んだ人が選べる。
- 結論（今回のおすすめ3つ程度）が先頭、根拠と一覧は後。
- 「出かけたくなる」書き出し。定型文でなく自然な文章。

実装方針:
1. スキル ikimono-weekend の「答えの組み立て」手順を、上の構成に書き換える。型（いつ・どこで・どの段階まで・どんな場所で・範囲の外）は維持する。
2. 検査器（ask verify）は事実（日付・段階・場所名・数値）だけを検査し、文章の言い回しは検査しない。事実の根拠のない具体（営業時間・料金・駐車台数など）は書かせない。読めなかった項目は「確認できていません」と短く書く。
3. 今週末の見込みは、取得できた見頃予測（日付つき）と現況から根拠を示して書く。根拠がなければ見込みは書かず、現況だけ書く。
4. 受け入れテスト（実通信は不要、記録済み入力で可）:
   - 「今週末に紅葉を見に行きたい」→ 先頭に結論3つ程度、狙い別の節、各候補に日付つきの根拠、内部用語なし。
   - 「今日、野鳥を見に行きたい」「今日、季節の花を見に行きたい」でも同じ構成になる。

## 3. 第2部: 情報源の台帳の発信者単位化と追加（別 commit）

1. 台帳（公式／紹介・予報に分離済み、段階46）を、URL 単位でなく**発信者（サイト運営元）単位**で数える形にする。同じ発信者の複数ページは1件として数え、定評の件数が水増しされないようにする。
2. 定評の条件に「公式の出どころ1件以上」を足す案があったが、上の共通の決まり（公式は確度ラベルであって条件ではない）と矛盾する。**条件には足さず**、公式の出どころが1件以上ある地点に「公式の確認あり」のラベルを付け、ない地点は「公式未確認」と添えるだけにする。
