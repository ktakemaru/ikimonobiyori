## 0. この作業の目的

2026-11-28 に、同じ質問を イキモノビヨリ・ChatGPT・イキモノビヨリを使わない Claude の 3 つに答えさせて比べた。
イキモノビヨリの答えは正直だが、挙がる場所の数がとても少なかった。

- 花の 4 問で、今年の様子を確かめられた場所は花菜ガーデンの 1 つだけだった。
- 紅葉では箱根と鎌倉が出ず、三溪園は公式の色づき情報のページがあるのに「確かめられていません」と答えた。
- ChatGPT は相模原公園・くりはま花の国の 11/27 の公式の開花情報を見つけた。

原因は答え方ではなく、探す範囲にある。名指しの質問(「大山の紅葉は?」)では Web を探すが、
開いた質問(「おすすめは?」「花を見たい」)では登録済みのページしか読んでいない。

### 本人の決定(2026-11-28)

1. 開いた質問でも、毎回 Web を広く探して候補を集める。
2. 候補は公式ページで日付と中身を確かめてから答えに書く。確かめられないものは「例年は」と書き分ける。
3. 確かめに使えた公式ページは、情報源の一覧に足していく。
4. そのぶん時間が延びるのは構わない。

「AI が答えを書き、コードが裏を取る」方向は変えない。裏取りの厳しさは下げず、候補の入口だけを広げる。

### 変えないこと

- 照合(ask verify)の決まりをゆるめない。照合を通すために検査の側を弱める変更はしない。
- 使わない出典の決まりはそのまま(tenki.jp、ウェザーニュースとその転載、バードリサーチ、山と溪谷オンラインの文章)。
  検索結果にこれらが出ても、ページは読まず、色づきの段階・見頃の予想・文章を答えの材料にしない。
- 写真のライセンスの範囲は変えない。
- 情報源の台帳の「承認」は本人だけが決める。この指示書には承認の指示は入っていない。
  Claude Code は承認も approved_by の記入もしない(第3部を参照)。
- 今までの ask answer(単体利用と控え)は消さない。
- 新しいライブラリは足さない。

## 第1部 開いた質問でも広く探す

### 1-1. 何を「開いた質問」とするか

場所を名指ししていない質問、または「横浜から行ける場所」のように範囲だけを言う質問。例:

- 週末のおすすめを教えて
- 横浜から行ける場所で紅葉情報を教えて
- 季節の花を見られるところはある?
- ツバキやサザンカが見られるところを教えて(対象は名指し、場所は開いている)

### 1-2. 流れ

開いた質問では、資料(brief)を作る前に、次の 3 段を毎回通す。

1. **手元を見る。** 登録済みの情報源から、聞かれた対象の今年の現況(日付つき)を全部集める。
2. **広く探す。** 聞かれた対象・季節・範囲で Web を検索し、「今その対象が見られそうな場所」の候補を集める。
   - 範囲は今までどおり(出発地から片道 250km 前後)。出発地に近い所だけで終わらせず、範囲全体から拾う。
   - 紹介サイト・観光協会の特集・まとめ記事は、**場所の名前を知るきっかけ**としてだけ使う。
     そこに書かれた色づきの段階や見頃は、この段では事実として扱わない。
   - 手元に今年の現況がある場所は、候補から外さない。
3. **公式ページで確かめる。** 候補ごとに、その場所の運営者・自治体・観光協会・ビジターセンターのページを探して読む。
   - 読めて、対象と日付が分かったもの → 今年の現況として記録する(日付つき)。
   - 公式ページはあるが日付が無いもの(月別の一覧など)→ 「例年の目安」として扱う。今年の現況にしない。
   - 公式ページが見つからない・読めないもの → 「未確認」として、名前・都県・例年の時期だけを添える(今の決まりどおり)。

名指しの質問で今ある流れ(feature/current-status-breadth)は変えない。同じ部品を、開いた質問からも呼べるようにする。
同じことをする別のコードを新しく書かない。

### 1-3. 探す量の目安

- 検索は 1 問あたり最大 8 回、ページの取得は最大 16 回を上限の初期値にする。
- 上限は設定で変えられるようにし、初期値と根拠(第5部の試し質問での実測)を報告書に書く。
- 公式ページの取得が 148 バイトなどで中身を取れなかったときは、今ある取り直しの手順を使う。
  それでも読めなければ「読めなかった」と記録し、検索結果の抜き書きを公式の内容として書かない。

### 1-4. 答えの組み立て

- 並べる順は、今年の現況がある場所(新しい日付の順)→ 例年の目安の場所 → 未確認の場所。
- **今年の現況がある場所は、その対象を聞かれたら必ず資料の候補に入れる。**
  (2026-11-28 の実例: サザンカを聞かれたのに、11/27 時点で見ごろと確かめていた花菜ガーデンが答えから抜けた。)
- 発信元どうしで内容が食い違うときは、片方に決めず、発信元と日付を添えて並べる(今ある決まりどおり)。
- 聞かれた範囲で対象が今の季節に合わないときは、そのことを先に言い、近い代わり(今見られるもの)を出す
  (富士山のまわりの花の答えは、この形でよくできていた)。

## 第2部 所要時間の予告を実際に合わせる

2026-11-28 の実例: 「約 24 秒」と予告して、実際は 3 分 14 秒かかった。予告なしで 3 分 2 秒かかった回もあった。

2. N は、第5部の試し質問で測った実測から決める(検索と取得、下書き、照合まで含めた全体の時間)。

4. 予告より 2 倍以上長くかかった回は、次の予告に反映できるように実測を記録に残す。

## 第3部 見つけた公式ページを情報源の一覧に足す

### 3-1. 足し方

第1部の 3 段目で、今年の現況を確かめるのに使えた公式ページは、情報源の台帳に**承認待ち**として記録する。

記録する項目(今の台帳の項目名に合わせる。足りない項目だけを足す):

- 発行元(施設の運営者・自治体・観光協会など)と、公式と判断した理由
- URL
- 何が書いてあるか(紅葉の色づき・開花・野鳥の記録 など)
- 日付の持ち方(記事ごとの日付あり/撮影日あり/日付なし)
- 更新のしかた(ブログ形式で記事が増える/1 ページを書き換える/月ごとに URL が変わる)
- 見つけた日と、きっかけになった質問

### 3-2. 足してよいページの条件

- 発行元が、その場所の運営者・指定管理者・自治体・観光協会・ビジターセンターのどれかだと、ページの中身から確かめられること。
- 確かめられないものは「紹介サイト」の区分にし、台帳には足さない(紹介サイトの名前は台帳に足さない、という今の決まりどおり)。
- 個人のブログ・SNS は足さない。
- 同じ発行元の別ページ(花・紅葉・野鳥・桜・ホタル)が近くにあれば、あわせて候補として記録する。

### 3-3. 承認の扱い

- Claude Code は承認の欄に何も書かない。承認待ちのまま記録する。
- 承認待ちのページの内容を答えに使えるかどうかは、第0部で調べた今の決まりに従う。決まりを変えない。
- 今の決まりでは使えず、そのために開いた質問の答えが広がらないと分かった場合は、
  決まりを変えずに止まり、「決めてほしいこと」として報告書に書く。
- 報告書に、この作業で足した承認待ちのページを表(id・発行元・URL・内容・日付の持ち方)で出す。
  本人がその表を見て、承認する id をチャットの指示文で伝える。

## 第4部 2026-11-28 の会話で見つかった小さな直し

第1部〜第3部とは別の commit にする。

1. **三溪園の花が古い。** 「見ごろの花」としてススキ・ノギク・ツワブキ・チャノキを答えたが、
   同じページではススキは 9 月、ほかは 10 月の欄で、ススキとツワブキには「見ごろ過ぎ」が付いている。
   月別の一覧を読むときは、聞かれた日の月の欄を使い、「見ごろ過ぎ」などの注記を落とさない。
2. **本文と出典の日付が食い違う。** 本文「いつの発信かは分からない」、出典「三溪園(11/9 時点)」。
   「〜時点」は発信日が分かるときだけ、読んだ日は「〜に確認」と書く。照合でこの食い違いを見つけられるようにする。
3. **出典の一覧が本文と対応していない。** 答えに使っていない発行元(利根川上流河川事務所、金沢市、東京都建設局 など)が出典に並び、
   使った発行元(花菜ガーデン)が「ほか 1 件」に入っていた。出典には本文の文に使ったものだけを出し、本文に日付つきで書いた発行元は名前を省かない。
4. **「これから」の見出しに、今が盛りのものが入る。** 冬桜(11 月中旬〜12 月初旬がいちばん良い時期)が「これから」に入っていた。
   見出しは、聞かれた日と例年の時期を比べて決める。
5. **島や船が要る場所の距離。** 大島公園を「直線で約 83km」と書いた。船か飛行機が要る場所は、直線距離だけを書かず、その旨を添える。
6. **天気への案内。** 週末のおすすめの答えに、天気の話が無かった。「天気はヤマビヨリで確かめてください」の一言を、
   山に限らず、出かける日の答えの最後に入れる(イキモノビヨリ自身は天気を答えない)。
7. **聞かれた日が今日のとき。** 土曜の朝に「週末」を聞かれたら、土曜は今日だと分かる書き方にする(開園時間に間に合うかの判断に関わる)。
8. **豆知識の量。** 1 つの答えに入れる一般の話は、見に行く人の役に立つものを 2 つまでにする(「花がらを摘むとまた咲く」のような育て方の話は入れない)。
9. **「1 failed」の表示(調べるだけ)。** 最初の質問で `Ran ... shell commands · 1 failed` と出た。
   どのコマンドが、どの終了コードで、なぜ 0 以外を返したかを調べる。
   「予定どおりの停止」で 0 以外を返している所の一覧と、その終了コードを見て動きを変えている呼び出し元(フック・テスト・スキルの手順)の一覧を報告書に書く。
   終了コードは「ビヨリ共通の約束」に関わるので、**この作業では変えない。**

## 止める条件

次のどれかに当たったら、そこで止まって報告書に書く。先へ進まない。

- `git status --porcelain --untracked-files=no` に、この作業で触るつもりのないファイルが出た。
- 照合(ask verify)を通すために、照合の側を弱める変更が必要になった。
- 承認待ちのページを答えに使うには、台帳の承認の決まりを変える必要があると分かった(3-3)。
- 使わない出典を読まないと候補が集まらないと分かった。
- 関係するテストが、直しを 2 回試しても通らない。
- C:\ikimonobiyori で別の Claude Code のウィンドウが動いていて、ブランチや未コミットの変更が混ざった形跡がある。

## テスト

- 作業中は、触った所に関係するテストだけを実行する。
- 最後に全テストを 1 回実行し、件数と結果を報告書に書く。時間がかかりすぎて終わらないときは、実行した範囲を正直に書く。
- Web に出る処理のテストは、通信なしで動く形にする(取得済みの内容を材料にする)。

2. 第2部(所要時間の予告)

4. 第3部の 3-4(候補のページの記録。データだけの commit)
5. 第4部(小さな直し。1〜8)
6. 報告書
