## 2. 第1部: エリア名の質問（「秩父・長瀞のエリア」「飯能あたり」）

1. **エリア辞書**: エリア名（秩父、長瀞、飯能、奥多摩、箱根、日光、富士五湖、軽井沢 など、関東・甲信越の主要な観光エリア）から、範囲（中心の座標と半径、または含まれる市区町村）と、含まれるカタログの地点を引く辞書を作る。座標は Wikidata（承認済みホスト）で確認できたものだけ。曖昧な名称（同名の別地域）は取り違えない。
2. **質問の解釈**: 「○○のエリア」「○○あたり」「○○周辺」を、エリア質問として扱う。エリア内の地点について、計画（`ask plan`）を作り、答えは**エリアの中での狙い別**（歩く・のんびり・夜・遠出など）にする。出発地（既定は横浜）からの距離の目安を添える。
3. **カタログにない地点**は、第10部（段階57）の流れで、公式の情報源を探して取得し、「仮」として記録する。
4. エリアの辞書にない名称のときは、「○○のエリアの範囲を特定できませんでした」と1文で伝え、近い名称の候補があれば、それを示す（確実なものだけ）。
5. テストを足す（合成データ、通信なし）: エリア名の解決、同名の取り違えがないこと、エリア内の地点が計画に入ること。

## 3. 第2部: 公式ページが分かったら、必ず取得して読む（最大150回）

1. **「中身は読めていません」を、取得を試みる前に書かない。** 検索の結果や計画に、**公式のドメイン**（自治体、観光協会、公園・施設の管理者、県・国の観光サイト）の URL が出たら、**取得して読む**。
2. 取得したページから、**関連する公式ページへのリンク**（「お知らせ」「紅葉情報」「イベント」「開園情報」など）を1階層だけ辿る（1回の質問につき最大6ページ。同日キャッシュ。同じホストへは1秒以上あける）。
3. 取得に失敗したとき（拒否・404・証明書の不一致）だけ、「公式ページを確認できていません」と書く。失敗を回避しない（別の経路で取りに行かない）。
4. 読めた事実のうち、**開園日・閉鎖・規制・変更**（「開園日等の変更」「一部区域の閉鎖」など）は、日付つきで、答えの「行く前に確認すること」に1行で入れる（文章の転載はしない）。
5. 読めた事実は、現況・実用情報として記録（データ置き場）に残し、同日の追質問で再取得しない。
6. テストを足す（合成データ、通信なし）: 公式 URL が出たとき取得の呼び出しが行われること／失敗したときだけ「確認できていません」になること／お知らせの変更が答えに出ること。

## 4. 第3部: 今年の情報がない候補と、古い年の記事の扱い

1. 今年（現在のシーズン）の情報がない候補（現況なし、今年の行事なし、今年の記載なし）は、「**今回のおすすめ**」に入れない。別枠「今年の情報が確認できていない候補」に、**1行ずつ**、事実（例年の見頃など、出どころの年を明記）だけを書く。
2. **古い年の記事（2024年・2025年・「去年」）を、おすすめの根拠にしない。** 参考として書く場合は、「2024年の記事では…」と年を明記し、今年の予測として書かない。
3. 計画（`ask plan`）の点数で、今年の情報がない候補を大きく減点し、おすすめ（3件）の対象から外す。
4. 検査器: おすすめ（①②③）の根拠が古い年の記事のみの場合は不合格にする。
5. テストを足す。

## 5. 第4部: SNS と作業の事情の文

1. **SNS（X、Facebook、Instagram、YouTube など）の投稿**を、**事実の根拠にも出典にも使わない**（過去の投稿も含む）。公式ページに「紅葉の状況は公式 SNS で更新します」と書かれている場合は、**その事実だけ**を、公式ページの URL を出典にして書く（SNS の URL や投稿の中身は書かない）。
2. 検査器に足す: 出典に x.com・twitter.com・facebook.com・instagram.com・youtube.com が含まれたら不合格。
3. **作業の事情の文**を、パターンで検出して不合格にする（段階57の第9部の規則を拡張）: 「このプロジェクトの方針で」「方針で使っていません」「検索結果にあった」「検索結果だけで」「外して検索」「ファイルは変更せず」「触れていません」「使っていません」（ホスト名と一緒に出る場合）。使えなかった情報の説明は、答えに書かない。
4. 連絡先（電話番号など）は、**取得した公式ページに書かれているものだけ**（段階57の第10部の規則を維持）。
5. テストを足す。

1. 会話の中で作った計画を、**直近5件まで・24時間**、リポジトリ外のデータ置き場に履歴として保存する（段階57の last_plan を拡張）。

5. テストを足す（合成データ、通信なし）。

## 7. 第6部: 場所名の表記ゆれと正式名称

1. 利用者の入力の表記ゆれ・略称・誤字（例: 「トーベヤンソンあけぼの子ども森林公園」→ 正式名称「トーベ・ヤンソンあけぼの子どもの森公園」）を、**場所の別名辞書**（カタログの名称と別名）と、必要なら公式ページの題名で、正式名称に解決する。解決できないときは取り違えない。
2. 答えの最初に、**正式名称**を使う。利用者の入力と正式名称が違うときは、1回だけ「（正式名称は○○です）」と示す。
3. 解決した別名は、データ置き場に記録して、次回から使う（既存の仕組みの範囲で）。
4. テストを足す（合成データ、通信なし）。

## 8. 第7部: 見頃を狙う週の提案（コードで計算）

1. 現況がない、または現況が古い地点について、例年の見頃の窓と、今年の傾向（周辺の現況、見頃予測があれば）から、「**見頃を狙うなら○週末**」を、**コードで計算**して出す（例: 例年の見頃のまん中を含む週末）。
2. 根拠のラベルを必ず付ける: 「例年の見頃（出どころ、区分）から」。今年の現況が分からないことを、同じ行に書く（言い切らない）。
3. 計算に使うのは、確認できた例年の見頃だけ。ないときは出さない。
4. テストを足す（合成データ、通信なし）。

## 8-2. 第9部: 複数エリア・日付の既定・冒頭の確かさ・下書きの骨組み（別 commit）

背景（2026-11-07 の会話の練習、通常の手順に戻した後）: 「大菩薩嶺・西沢渓谷、秩父～長瀞～飯能、富士山周辺などで紅葉のおすすめを探しています。」に対して、長瀞の公式の現況は取得できて良かったが、次の点が残った。

- 質問の5つのエリアのうち、飯能と大菩薩嶺は「ほかの地域」の1〜2行に偏った。
- 日付の指定がなく、答えは今週末（11/7〜8）として答えたが、その旨が書かれていない。「探しています」型なので、今週末と来週末の両方を出すほうが親切。出発地も明記されていない。
- 冒頭は「楽しめそうです」と言い切る一方、おすすめの②は「今の色づきの状態は確認できていません」。冒頭が、最も弱い確かさに合っていない。
- ③西沢渓谷のおすすめは、ウォーカープラスの「今見頃」（公式でない。現況の提供元がページごとに違い、JRシステムやウェザーニュース由来のこともある）が主な根拠になった。
- 初回の下書きが、検査に**9件**落ちた（エージェントが手で直して再検査）。下書きの質を、コードで底上げしたい。

1. **複数エリアの質問**: 「A・B、C〜D〜E、F周辺など」を、エリアに分解する（区切りは「、」「・」「,」「〜」「～」と「など」「あたり」「周辺」）。各エリアの計画を作り、答えは**エリア別の節**にする（各エリア1〜2件、「今回のおすすめ」3件は、エリアが分散するように選ぶ）。**質問に挙がったエリアは、どれも漏らさず**触れる（検査で、質問のエリアが答えに出ていることを確かめる。現況がないエリアも、「確認できていません」と1行書く）。
2. **日付の既定と明記**: 日付の指定がなければ、既定は「今週末」（今日が土日なら今日と明日、平日なら次の土日）。答えの冒頭に、**「日付の指定がなかったので、○/○〜○/○で探しました」**と1文で書く。「探しています」「行きたい」のような、計画段階の質問（日付なし）は、**今週末と来週末の両方**を出す（期間別の節。段階57の第9部の2期間の仕組みを使う）。出発地も、段階57の第8部のとおり、使った出発地を明記する。
3. **冒頭の確かさ**: 冒頭の文は、「今回のおすすめ」3件のうち**最も弱い確かさ**に合わせる。現況が確認できていない候補が含まれるときは、「楽しめそうです」と言い切らず、「現況が確認できている場所と、できていない場所があります」のような、確かさに合った文にする。検査器で、冒頭が断定で、現況なしの候補を含むなら不合格にする（段階56の規則の再確認とテスト）。
4. **第三者サイト（ウォーカープラス・ジョルダン・るるぶなど）の現況**: 「今見頃」「色づき始め」などの現況は、**おすすめの採用理由にしない**。公式の現況（自治体・観光協会・施設・県の観光サイト）があれば、そちらだけを使う。公式の現況がないときは、「紹介サイトでは○○とされています（公式ではありません）」と**1行の参考**にとどめ、確かさにも反映する（現況なしとして扱う）。ページに提供元の表示があり、**ウェザーニュース・tenki.jp・日本気象協会**と読める現況は、使わない。提供元が不明のものは、参考扱い。
5. **下書きの骨組みをコードで作る**: 計画から、答えの**骨組み**（冒頭の文、日付・出発地の1文、「今回のおすすめ」、エリア別・狙い別の節、まつりの行、確かさの補足、出典、末尾の提案）を、コードが組み立てる。エージェントは、骨組みの文を、**事実を追加・変更せず**、自然な日本語に整える（言い回しの調整だけ）。事実の追加・差し替えは、第1部（段階56）の override の記録を通す。
6. **初回の検査不合格数を測る**: 答えを作るたびに、初回の ask verify の不合格数を記録し（データ置き場）、回帰テストの指標にする。骨組みから作った答えは、**初回で検査に通る**（不合格0件）ことを目標にし、回帰テストの合成データで確かめる。
7. テストを足す（合成データ、通信なし）: 複数エリアの分解と、漏れの検出／日付の既定と明記／冒頭の確かさの検査／第三者の現況が採用理由にならないこと／骨組みが初回の検査に通ること。

### 9-追加. 初回の検査10件の分析（2026-11-07）と対策

実測: 初回の検査は**10件**落ちた（`unknown_date` 2、`too_few_candidates` 1、`no_typical_in_candidate` 1、`source_unused` 4、`practical_fallback_missing` 1、`repeated_phrase` 1）。書き直し後も2件（`too_few_candidates`、`no_typical_in_candidate`）が残り、**検査を通らない文を除いた版（final.txt）**が利用者に出た。西沢渓谷・大菩薩嶺・天覧山がカタログの候補になっていなかったことが、候補不足の原因。

- **a. 決まり文・語の重複・出典は、コードが入れる**: 「確かさの補足」の決まり文（実用情報が1件も取れないときの一文など）、「公式ではありません」の**1回化**、出典リストは、骨組みでコードが入れる。**出典は、本文で使った事実（facts）の出どころから、コードが作る**（エージェントが手で書かない）。これで `practical_fallback_missing`、`repeated_phrase`、`source_unused`（4件）を、初回から解消する。
- **b. 未記録の事実を書かない**: 答えに書く日付つきの事実（例: 「遊歩道は12/1〜4/28が冬期閉鎖」）は、**先に記録**（カタログにない場所は、仮の候補として。段階57の第10部）してから使う。記録のない日付・事実は書かない。これで `unknown_date`（2件）を解消する。検索で見つけた事実を、記録せずに文章に入れる手順を、スキルから取り除く。
- **c. 候補数の扱い（`too_few_candidates`）**: 最低3件の規則は、「**利用できる（記録のある）候補の数**」に合わせる（`min_candidates = min(3, 利用できる候補数)`）。3件に満たないときは、骨組みの決まり文で「この地域で今年の情報が確認できた候補は○件です」と示す。**ただし候補を増やす努力が先**: カタログにない場所（西沢渓谷、大菩薩嶺、天覧山など）は、公式の情報源を取得し、仮の候補として記録して、候補に数える（段階57の第10・11部、第1部のエリア辞書）。候補が少ないことを、書き手が埋め合わせようとして未記録の候補を足さない。
- **d. 例年の見頃（`no_typical_in_candidate`）**: 各候補に例年の見頃を書く規則は維持する。例年の見頃が確認できない候補には、**決まり文をコードが入れる**（「例年の時期は分かりません」の形）。例年の見頃は、段階56の第3部・段階57の第11部（山梨県の「見頃」列）で補う。
- **e. 検査を通らない答えを出さない**: 再検査後も不合格が残るときは、「検査を通らない文を除いた版（final.txt）」を出す運用をやめる。代わりに、**骨組みから作った最小の答え**（検査に通る形。候補は利用できる分だけ、確かさを明記）を出す。それも作れないときは、「今は答えを用意できません」と1行で伝える。スキルの該当手順を書き換える（検査の再実行は、1回の書き直しまで、は維持してよい）。
- **f. テスト**: 初回の検査で、上の10件の型（決まり文の読点違い、語の重複、出典と事実の不一致、未記録の日付、候補不足、例年の見頃なし）が、骨組みで再現しないこと。候補不足の決まり文が検査に通ること。不合格が残るとき、最小の答えが出ること（通らない文を除いた版が出ないこと）。
