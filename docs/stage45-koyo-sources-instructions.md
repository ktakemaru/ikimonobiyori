## 1. 守ること（既存の決定を変えない）

- 情報収集のための通信は、今回の開発では承認を求めずに行ってよい（ユーザー決定 2026-10-31）。今回追加する通信先は次の2ホスト。これはユーザーがこの指示書で承認したものとして、data-sources.md と CLAUDE.md / AGENTS.md の承認ホストの一覧に、承認日（2026-11-04）つきで追記する。
  - koyo.walkerplus.com
  - n-kishou.com（および s.n-kishou.co.jp は、読めることを確認できた場合のみ）
- robots で拒否されるサイトや、転送・Cookie 前提で読めないページを、回避する工夫（別経路・キャッシュ・ミラー）で読まない。読めないものは「読めない」と台帳に記録して止める。
- WebFetch には、状態の見出しと「○/○現在」の日付を書かれたとおりに抜き出させる。紹介文から推測させない。答えは原文の表記で示す（段階16の修正点②）。
- 新しいライブラリは足さない。
- 答えに内部の用語（reader、record、status_log、policy.yaml など）を出さない。使う人には「何月何日時点か」と「出どころの種類」だけを示す。
- 作業中は関係するテストだけ実行し、全テストは CI に任せる。
- 開始前に、現在のブランチが main で未コミットの変更がないことを確認する（別ウィンドウの Claude Code が同じフォルダを使っている可能性がある）。問題があれば止まって報告する。

### 4-2. 読み方の確認（最初に実物で確かめる）
トップページでは、各地点の色づき段階が見えるかどうか未確認。次を確かめて報告書に書く。
- 上の一覧ページに、地点ごとの色づき段階と更新日が出るか。
- 出ない場合は、個別ページ（https://koyo.walkerplus.com/detail/... の形）に出るか。一覧から個別ページへ辿る形で読めるか。
- WebFetch が少ないバイト数（148バイトなど）しか返さない場合は、その事実を記録し、検索の要約に頼る代わりに、別の読み方（一覧の項目名と段階だけを抜き出す指示など）を試す。それでも読めなければ読めないと記録する。
- ページの構造が安定していて決まった形で読めるなら、日光・箱根と同様にコードで読む案を報告書に提案する（実装は、テストが書ける場合のみ。判断に迷えば提案だけ）。

## 6. 答えの条件
- 「神奈川でおすすめの紅葉」の答えは、候補を3件以上出す。紹介サイトの候補には「公式ではありません」「○月○日時点」を添える。
- 結論（おすすめ）を先に、根拠と一覧は後にする。
- 読んだ事実は必ず status_log に記録する（修正点④）。
- 内部の用語を答えに出さない。

## 7. 受け入れテスト（実通信で行い、結果を報告書に書く）
1. 「明日 紅葉を見に行きたい。神奈川でおすすめを教えて」→ 候補3件以上。出どころの種類と日付がある。
2. 「今週末 紅葉のおすすめ」→ 神奈川だけでなく、他県の候補も出る。
3. 「東京で今見られる紅葉」→ 都内の候補が3件以上。夜間特別開園の情報が添えられている場合は、その日付も正しい。
4. 追加前と追加後で、手順1の候補の数と出どころの数を比べて報告書に載せる。
