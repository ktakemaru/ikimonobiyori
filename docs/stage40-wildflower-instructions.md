- **トークンが限られている。** 山域ごとに完結させ、**山域ごとにコミット**する。順番は 丹沢 → 箱根 → 奥多摩 → 高尾 → 余力があれば 富士山周辺 → 八ヶ岳 → 南アルプス → 北アルプス。途中で止まっても壊れないこと（終えた山域だけが入っていればよい）。

## 1. 範囲の絞り込み（利用者の決定 2026-11-03）

- **花が咲くことを楽しめる野草・高山植物に絞る。** 草本が中心。高山の低木（シャクナゲ類・ミツバツツジ類など、登山者が花を目当てにするもの）は含めてよい。シダ・コケ・花を目当てにしない樹木は対象外。桜・梅などは既存のテーマに任せる。
- 目的: **将来、ビヨリコンシェルが「登山のおすすめポイント」として花の情報を合わせて提案できる**こと。ヤマビヨリ（山の天気）が山を選び、イキモノビヨリが「その山で、この時期に、どの高さで、どんな花が例年見られるか」を添える。
- 今年の開花状況は追わない。例年の時期（月・旬）の目安でよい。

## 2. コンシェルジュが使える形で出す（最重要の追加）

### 2-1. 地点の鍵をヤマビヨリと揃える
- `ikimonobiyori/data/sites.yaml` の山・山域 76 地点の識別子（ID・名前・座標・標高・山域）を**そのまま鍵に使う**。独自の名前を作らない。山域のまとまりは `sites.yaml` の持つ区分に従い、無ければ最小の対応表（`data/guide/wildflower_areas.yaml`）で、各地点を山域に結ぶ。

### 2-2. 機械が読める出力と、そのまま添えられる短い文
- 新しいコマンド `python -X utf8 -m ikimonobiyori.guide wildflower --site <地点ID> | --area <山域名> [--month N | --date YYYY-MM-DD] [--json]`。
  - `--json`: 次の項目を持つ決まった形（スキーマは `ikimonobiyori/schemas/` に足し、jsonschema で検査）。`site`（ID・名前・標高）、`month`、`flowers[]`（和名・学名・taxon id・標高の範囲・例年の時期（開始旬〜終了旬）・見分けの一言・注意・確度（独立した出どころの数）・出どころ（URL・読んだ日・区分）・写真の有無）、`season_note`（例年の目安である旨）、`caveats[]`。
  - 既定（テキスト）: **コンシェルジュが山の提案にそのまま足せる 1〜3 文**（例: 「この時期は標高○○m付近で□□・△△が例年見られます」）と、必要なら「例年の時期の目安です。今年の開花は読めていません」。内部用語を含めない（B-2）。
  - 該当がなければ、空の結果と「データ準備中」を返す（嘘を作らない）。
- `--month` の既定は今日の月。標高が高いほど時期が遅れる点は、出どころのあるときだけ書く。
- 山の天気・コース・危険箇所は扱わない。「ヤマビヨリで確かめてください」の一言まで（B-7）。
- このコマンドが、ハブ側で将来コンシェルジュに繋がる**唯一の入口**になる。ハブは変更しない（第2部は別の機会）。ただし `C:\biyori-hub` の既存の「他ビヨリの呼び方」（`agents/*/manifest.yaml` や `CLAUDE.md` の記述）を**読むだけ**で確かめ、呼びやすい形になっているかを報告書に1段落で書く。

### 2-3. 組み合わせの例を1つ作っておく
- `docs/` に、ヤマビヨリの山の候補 1 つに対し、`guide wildflower --json` の出力を添えた**提案文の例**（コンシェルジュの出力イメージ）を1つ書く。ヤマビヨリの出力は例として手で書いてよい（実通信しない）。

## 3. 知識の作り方（6章の要点＋変更）

- 出どころはネット上の公開情報（国立公園・自治体・観光協会・ビジターセンター・植物園/博物館・環境省・登山口/山小屋/ロープウェイ運営者・登山の専門メディア）。WebSearch/WebFetch は確認なしで使う。取得が 148 バイトなど内容のない応答なら、読めた扱いにせず、別ページを1回試し、だめなら「取れなかった」と記録する。
- 事実だけを記録し、本文の写しや写真は残さない。**独立した出どころ2件以上で「定評」、1件は「仮」**（方針の値、`provisional`）。個人の登山記録は `secondary`。
- 種のカード（和名・学名・taxon id・科・標高の範囲・例年の時期・環境・見分け・似た種・注意・出どころ・確度）を、山域ごとの花暦（山域×月（旬）×標高帯）にひも付ける。保存先と形式は 6章 D-3・D-4 のとおり（`data/guide/` に `wildflower_taxa.yaml`・`wildflower_facts.yaml`・`wildflower_calendar.yaml`、スキーマは `schemas/`）。
- **質を優先**: 出どころの付かない種は入れない。1山域あたり 20〜40 種を目安（`provisional`）。量より、花暦の月・標高帯の穴が少ないことを優先する。
- **保護**: ラン科や高山の希少種は、地点を出さず山域まで。答え・JSON の `caveats` に「採らない・登山道から出ない・踏まない」を必ず入れる。
- iNaturalist の月別・標高帯の観察集計（D-5）は、**余力があれば最後に**。通信は承認B（確認なし）の範囲、間隔 1 秒以上・1回 80 件以内。観察者・正確な座標・写真の URL は保存しない。なければ文献の花暦だけでよい。
- 写真（D-8）も余力があれば。種ごとのキャッシュに載せる（承認B）。希少種は位置が特定されないものだけ。

## 4. 答え方（質問の型）

- 「野草・山野草・高山植物・お花畑が見たい」「〇月に〇〇山で見られる花は」などの話題を登録し、`ask` の経路からも `guide wildflower` を使って答える（検査を通す。内部用語を出さない。聞き返しで終えない）。
- 答えの形は 6章 D-6 のとおり。ページ（Artifact）を頼まれたら、種の写真つきページ（キャッシュにあるものだけ。無ければ「写真なし」の行）。
